# Исполнитель операций AppSec.Hub

Сейчас запросы к Hub выполняет исполнитель (режим для схемы, когда Hub виден с другого компьютера).
Основной режим – прямая работа приложения с Hub под учётной записью оператора – в разработке,
ADR-0129. В схеме с исполнителем статусы находок и дефекты отправляет
этот скрипт. Его запускают там, где виден Hub:

- **в виртуальной машине с VPN**, если приложение работает на другом компьютере, который Hub не видит;
- **на том же компьютере**, где стоят Docker Desktop и приложение, если VPN поднят прямо на нём.

Исполнитель входит в Hub под вашей учётной записью, забирает у приложения задания (сам обращается к приложению –
входящие соединения не нужны) и выполняет каждое: один запрос к REST Hub из белого списка. Ответ Hub уходит
приложению как есть, решает всё приложение и вы.

## Версия 0.9.25.dev2

Контракт полного PUT сохраняет числовые времена и severity связанных находок из GET установленного Hub. Правила ввода редактируемых полей проверяются отдельно. Для отправки этой формы замените файл исполнителя на версию 0.9.25.dev2.

Исполнитель передаёт `sync_protocol=2` в каждом запросе задания. Приложение восстанавливает совместимость после собственного перезапуска; старому исполнителю `sync_read` не выдаётся. Возвращение исполнителя не продолжает прерванное чтение без подтверждения оператора.

Для синхронизации разрешён только GET: `/issue/v2` (appIds, pageIndex, pageSize, sort, необязательный ignoreBranchFilter), SAST/SCA Security/SCA Compliance по ID (необязательная branch), DAST по ID, `/issue/status` (issueId, issueType), riskAcceptance и comment по типу/ID, `/defects` (appId, pageIndex, pageSize, необязательный sort), `/defects/{id}`. Параметры проверяются и кодируются одинаково с приложением. Проверка протокола и независимого app_id выполняется до HTTP. Одно задание выполняет ровно один запрос; повторяется только доставка его результата приложению.

Проверка `/auth/user` по таймеру удалена. При 401 запрос не повторяется, работа завершается; для нового входа оператор запускает исполнитель явно. Предел ответа 1 МиБ сохранён; усечённая страница оставляет чтение неполным; усечённый подробный ответ сохраняется исключением объекта, остальные объекты читаются.

Приложение запускает чтение после подтверждения оператора с адаптером по замеру установленного Hub. Запрос списка находок не передаёт ignoreBranchFilter, список дефектов не передаёт sort. Протокол 1 эти формы не принимал, поэтому нужен новый файл исполнителя; в этой сборке номер версии 0.9.25.dev2. Старые незавершённые запуски протокола 1 следует закрыть и начать новый обход.

Исторический SHA-256 версии 0.9.25.dev2 (UTF-8, LF): `e1700d2690e92aa40288728fdfbad4810c44c04657c1d0658bfa4f8ee695bfab`. Результаты проверки: протокол сборки.

## Что нужно

- Python 3.11 или новее (сторонние пакеты не нужны);
- доступ к Hub с этой машины (VPN) и к приложению по сети;
- три файла из этой папки: `hub_worker.py`, `hub_worker.conf`, `hub_worker.cmd`.

## Запуск

1. В приложении: «Настройки» → раздел «AppSec.Hub» – укажите адрес Hub, сохраните, нажмите «Скопировать ключ».
2. Откройте `hub_worker.conf` в блокноте и заполните четыре строки:
   - `app_url` – адрес приложения, как он открывается в браузере на этой машине: в виртуальной машине – адрес
     компьютера с приложением (например `http://192.168.0.10:8765`), на том же компьютере – `http://127.0.0.1:8765`;
   - `hub_url` – тот же адрес Hub, что в «Настройках» (только `https`, без пути);
   - `login` – ваш логин в Hub;
   - `key` – ключ из «Настроек».
3. Запустите `hub_worker.cmd` (двойным щелчком) и введите пароль Hub – ввод скрыт.
4. В окне появится «вошли в Hub как …» и «на связи с приложением». В «Настройках» приложения исполнитель
   показан как «на связи»; кнопка «Проверить связь» за 1–3 секунды покажет ваше имя и роли в Hub.

Окно оставьте открытым, пока работаете: в нём видно каждое задание – метод, путь, код ответа Hub и время.

## Остановка

`Ctrl+C` в окне исполнителя: он выходит из Hub («выход из Hub выполнен») и закрывается. Задание, которое в этот
момент выполнялось, приложение покажет как «результат неизвестен» и предложит сверить – повторно в Hub оно само не
уйдёт.

## Что исполнитель хранит и чего не делает

- Пароль спрашивается при запуске, используется для входа и сразу забывается. Если сессия Hub истечёт, работа завершится;
  новый вход выполняется отдельным запуском оператора. В файлы, журнал и приложение пароль не попадает.
- Cookie сессии Hub живёт только в памяти процесса.
- Ключ исполнителя лежит в `hub_worker.conf`; если ключ выпустили заново в «Настройках», впишите новый и
  перезапустите исполнителя. Сеть считается доверенной (как доступ к приложению из сети по
  ADR-0103): ключ защищает от случайного процесса, а не от
  целенаправленного.
- Запросы – только из белого списка (тот же, что в приложении): чтение пользователя, находок, статусов и дефектов,
  смена статуса находки, создание дефекта и привязка к нему находок, с версии 0.9.23.dev4 – обновление заголовка и
  описания существующего дефекта (`PUT /defects/{id}`, кнопка «Обновить в Hub» во вкладке «Дефекты»). `DELETE` и
  другие `PUT` не выполняются вовсе; задание вне списка не выполняется, приложению уходит ответ «не отправлено».
  Исполнитель прежней версии `PUT` не выполняет: приложение покажет «обновите исполнитель в ВМ».
- Перенаправления не выполняются: ключ и cookie не уйдут на чужой адрес.
- Запрос к Hub выполняется один раз. Если приложение недоступно, повторяется только доставка ответа (до 15 минут).
- В окне нет тел ответов, ключа, cookie и пароля.

## Если что-то не так

| В окне | Что сделать |
|---|---|
| «Нет файла настроек» / «нет ключа» / «нет логина» | заполните `hub_worker.conf` |
| «Ввод нельзя скрыть в этом окне» | запустите из обычной командной строки `cmd`, не из редактора |
| «Hub недоступен» | проверьте VPN и адрес Hub |
| «Вход в Hub не удался» | проверьте логин и пароль; учётная запись должна входить в Hub по паролю |
| «Приложение не принимает ключ» | скопируйте ключ заново в «Настройках» |
| «Приложение недоступно по адресу …» | проверьте `app_url`: откройте его в браузере на этой машине |

## Версия 0.9.24.dev2: поля и справочники дефекта

Для dev1b ADR-0126 требуется заменить `hub_worker.py` и перезапустить исполнитель. Настройки и ключи остаются прежними. Установку в ВМ выполняет оператор.

| Метод и путь относительно `/hub/rest` | Назначение |
|---|---|
| `GET /defects/serviceInfo` | Имена приоритетов; существующая пара белого списка |
| `GET /application/{id}/structureUnits` | Структурные единицы приложения; новая пара |
| `GET /releaseObject/filters?appId={id}` | Варианты единиц и объектов выпуска; новая пара |
| `PUT /defects/{id}` | Полный DefectDto с явными правками черновика; существующая пара |

Три справочных запроса имеют назначение `defect_reference`. Приложение показывает их и ставит в очередь только после подтверждения оператора. Каждый выполняется один раз. У задания есть отдельное поле `app_id` из сохранённой операции. Исполнитель проверяет integer/int64, совпадение ID в пути или query, ровно один `appId` без дополнительных параметров и отсутствие тела GET. Отсутствующий или несовпавший контекст даёт «не отправлено» до HTTP к Hub.

Новые PUT помечены `contract_version=defect-fields-v1`. Исполнитель проверяет обязательные и известные вложенные свойства полного объекта, точные типы, даты с зоной, ID пути и приложение. Неизвестные расширения сохраняются; `null` не заменяется пустым значением. Приложение отвечает за разрешённые правки, diff и подтверждающее чтение. Старые задания без маркера сохраняют контракт dev1. Автоповтора PUT нет; доставка результата приложению сохраняет прежнее поведение.
