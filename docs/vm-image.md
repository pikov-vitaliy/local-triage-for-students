# Образ ВМ «Локального триажа»

## Зачем образ и что внутри

Образ – готовая виртуальная машина VMware (файл `.ova`), в которой «Локальный триаж» работает сразу после
включения, без Docker Desktop и без Ollama на компьютере пользователя. Он нужен в двух случаях:

- **показ**: в приложении уже есть демо-проект на выдуманных данных (`examples/demo`) с ответами по SCA; если
  при сборке была доступна большая модель, он разобран ею на компьютере с видеокартой и вердикты с объяснениями
  видны сразу, иначе демо разбирается при показе маленькой моделью в ВМ;
- **работа в своём контуре**: в ВМ клонируются настоящие репозитории, загружается настоящая выгрузка, разбор
  идёт моделью внутри ВМ.

| Что | Где в ВМ |
|---|---|
| ОС | Ubuntu Server 24.04 LTS, имя хоста `local-triage-demo`, учётная запись `triage` (группы `sudo`, `docker`) |
| Приложение | контейнер `local-triage` из образа `local-triage:<версия>`, порт 8765 только на 127.0.0.1 ВМ; с компьютера – через SSH-туннель |
| Модель | контейнер `local-triage-ollama`: Ollama только для процессора и модель `qwen2.5-coder:3b`; сеть Docker закрытая, выхода наружу нет |
| Файлы приложения | `/opt/local-triage/`: `docker-compose.yml`, `docker-compose.vm.yml`, `.env` (в нём `POSTGRES_PASSWORD`: случайный, у каждой копии свой, создаётся при первой загрузке), `REVISION` (коммит) |
| Данные приложения | `/opt/local-triage/data`: копия демо-базы `demo.dump`, ключ маскирования и то, что создаёт работающее приложение; постоянная папка на диске ВМ |
| Модели Ollama | `/opt/local-triage/ollama` |
| Клоны репозиториев | `/srv/repos` (владелец `triage`); приложение видит папку только на чтение. Демо – `/srv/repos/demo/examples/demo` (выгрузка, ответ SCA, клоны в `repos/`): там его находит кнопка «Создать демо-проект», которая ищет `examples/demo` не глубже двух уровней от корня |
| Запуск | служба `local-triage.service` при каждой загрузке, `local-triage-refresh.timer` раз в две минуты |
| Сеть | DHCP на любом адаптере `en*`, в образе – мост (bridged) |
| Оборудование | 4 vCPU, 8 ГБ памяти, растущий диск 80 ГБ (LVM на весь диск), VMXNET3 |
| Часовой пояс | UTC |

У интерфейса нет входа по паролю: кто достучался до порта, тот читает находки и код, меняет решения и удаляет
проекты. Проверки имени хоста и источника запросов (`Host`, `Origin`) защищают от чужих страниц в браузере,
но не удостоверяют пользователя. Поэтому порт 8765 опубликован только на 127.0.0.1 ВМ (`TRIAGE_BIND=127.0.0.1`
в `/opt/local-triage/.env`), а с компьютера приложение открывается через SSH-туннель – раздел «Доступ
к приложению». Открыть порт в сеть можно, но только с ограничением источника и до загрузки настоящей выгрузки.

Если порт открыт на адрес ВМ, приложение принимает запросы только с разрешёнными именами хоста – адрес ВМ
и `local-triage-demo`. Адрес ВМ приходит по DHCP, поэтому сценарий `/opt/local-triage/bin/start.sh` при каждой
загрузке и раз в две минуты вписывает его в `TRUSTED_HOSTS` (при `TRIAGE_BIND=127.0.0.1` адрес не вписывается:
127.0.0.1 и `localhost` приложение принимает всегда) и, если строка сменилась, пересоздаёт контейнер приложения.
Ставить перед приложением обратный прокси, который меняет заголовок `Host`, нельзя: проверка источника запросов
(`Origin`) начнёт отклонять действия.

Состояние ВМ видно с компьютера без входа в неё:

```bash
vmrun -T ws readVariable <файл.vmx> guestVar triage.status     # loading | ok | load-failed | db-password-failed | db-failed | db-restore-failed | compose-failed | bind-unconfirmed | bind-reverted | stopped-bind-unconfirmed | stop-failed | app-not-responding
vmrun -T ws readVariable <файл.vmx> guestVar triage.ip
vmrun -T ws readVariable <файл.vmx> guestVar triage.machineid
vmrun -T ws readVariable <файл.vmx> guestVar triage.hostkey     # ключ SSH сервера ed25519: сверка ключа при первом входе
```

## Требования к компьютеру сборки

- Windows, VMware Workstation Pro: `vmrun`, `vmware-vdiskmanager`, `ovftool` из комплекта.
- Git Bash, Docker Desktop (в нём и временный контейнер PostgreSQL шага `data`), Python из `.venv` репозитория (`pip install -r requirements-dev.txt`) и Python
  с `paramiko` для проверки входа по SSH и SSH-туннеля к приложению (переменная `PY_SSH`, по умолчанию `python`).
- Ollama на этом компьютере с большой моделью для демо-данных (по умолчанию `gpt-oss:20b`) и видеокартой.
- Выход в интернет: обновления Ubuntu, Docker, git, базовые образы контейнеров, маленькая модель.
- ISO `ubuntu-24.04.5-live-server-amd64.iso` с releases.ubuntu.com, SHA256 сверяется по опубликованной.
- Сеть ВМ – только мост (VMnet0) на проводной адаптер с DHCP. Host-only (VMnet1) и NAT (VMnet8) не
  используются: на одном из сборочных компьютеров включение ВМ на VMnet1 вызывало сбой Windows.
- Рабочая папка и папка выдачи – только с латиницей в пути: `ovftool` не читает и не пишет файлы, если в пути
  есть кириллица (ответ `Failed to read from file`). Пробелы и скобки не мешают.
- Права администратора не нужны.

## Пересборка

Сценарии лежат в [`deploy/vm`](../deploy/vm):

| Файл | Что делает |
|---|---|
| `build.sh` | шаги сборки, проверка и цепочка `all` |
| `prepare_demo_data.py` | проверки на компьютере сборки: `check` – приложение из чистой копии открывает базу, восстановленную из `demo.dump` (демо-проект с вердиктами или без, «Создать демо-проект»), `probe` – проба маленькой модели на пустой базе |
| `demo_db_build.py` | база образа – заново в пустой базе PostgreSQL, только из демо-данных `examples/demo`; вердикты демо – только прогон большой модели во время сборки (модель недоступна – без вердиктов); готовая база не принимается |
| `demo_db_check.py` | последняя проверка состава базы для образа (соединение только на чтение): только демо-проект из `examples/demo`, всё постороннее, в том числе таблицы в других схемах, – отказ |
| `secret_file.py` | файлы с секретами только для владельца: файл создаётся сразу с такими правами (0600; на Windows – защищённый список разрешений с одной записью текущего пользователя, без наследования, без совместного доступа), затем проверка (ровно одна запись) и только потом запись секрета; существующий файл не перезаписывается – замена только явная (`prepare_secret` и `commit_secret`, атомарно); `restrict` – для `build.sh` |
| `check_app.py` | проверка приложения через SSH-туннель: главная страница, демо-проект, вердикты у всех находок SAST или ни у одной (`--expect-verdicts`); с ключами – «Создать демо-проект», живой разбор, «Спросить модель» |
| `ssh_tunnel.py` | SSH-туннель к 127.0.0.1:8765 в ВМ на время одной команды, ключ сервера – строго по файлу из guestinfo |
| `first_login.py` | первый вход по паролю: система требует сменить пароль; с `--change` – смена на случайный (в файл) |
| `ollama-cpu/Dockerfile` | Ollama того же выпуска без библиотек видеокарт (около 200 МБ вместо 9 ГБ) |
| `autoinstall/` | ответы автоустановки Ubuntu и меню загрузки ISO |
| `guest/` | файлы ВМ: compose-дополнение, `.env`, службы, `start.sh`, `cleanup.sh`, `network-access.sh` (доступ по сети с проверкой ограничения), сеть, настройки VMware Tools |
| `local-triage-demo.vmx` | оборудование ВМ |

Одной командой (из корня репозитория, Git Bash):

```bash
REV=<коммит или тег> deploy/vm/build.sh all
```

Отметки шагов – в `<BUILD>/logs/chain.out`, вывод каждого шага – в `<BUILD>/logs/step-<шаг>.out`, общий журнал –
`<BUILD>/logs/build.log`. Остановилось – исправить причину и продолжить с этого шага командой шага.

Параметры (переменные окружения, значения по умолчанию – в начале `build.sh`):

| Переменная | Значение |
|---|---|
| `REV` | коммит приложения, из которого собирается образ (`git archive`, рабочая папка не используется) |
| `BUILD` | рабочая папка сборки: копия приложения, архивы, ISO, журналы, `secrets`, выдача в `out` |
| `VMDIR`, `CHECKDIR` | папки сборочной ВМ и проверочной копии |
| `ISO_SRC`, `ISO_SHA256` | исходный ISO Ubuntu и его опубликованная сумма |
| `SMALL_MODEL` | модель в ВМ, по умолчанию `qwen2.5-coder:3b` |
| `BIG_MODEL`, `HOST_OLLAMA` | модель и адрес Ollama сборочного компьютера для вердиктов демо |
| `DEMO_VERDICTS` | `auto` (по умолчанию) – вердикты демо прогоном `BIG_MODEL` при сборке, модель недоступна – образ без вердиктов с пометкой в журнале; `require` – без модели отказ; `none` – без прогона |
| `DB_BUILD_CONTAINER`, `DB_BUILD_PORT` | имя и порт на 127.0.0.1 временного контейнера PostgreSQL шага `data`, по умолчанию `lt-build-db` и 5436 |
| `DISK_GB` | размер растущего диска, по умолчанию 80 |
| `PY` | Python с зависимостями приложения |
| `PY_SSH` | Python с `paramiko` для проверки первого входа |

По шагам:

```bash
deploy/vm/build.sh src        # чистая копия приложения (git archive REV) в <BUILD>/src
deploy/vm/build.sh images     # образы local-triage:<версия>, базы и local-triage-ollama-cpu, архивы для ВМ
deploy/vm/build.sh model      # маленькая модель в <BUILD>/stage/ollama
deploy/vm/build.sh data       # demo.dump заново из демо-данных (временный PostgreSQL), вердикты – прогон большой модели при сборке
deploy/vm/build.sh iso        # ISO с автоустановкой и всем перечисленным
deploy/vm/build.sh vm         # диск и .vmx в сборочном варианте
deploy/vm/build.sh install    # автоустановка, ВМ выключается сама
deploy/vm/build.sh firstboot  # первый запуск, проверка приложения через SSH-туннель (только чтение)
deploy/vm/build.sh finalize   # итоговое оборудование, проверки, состав ПО, очистка, выключение, маркер выпуска
deploy/vm/build.sh export     # OVA и SHA256 в <BUILD>/out – только после подтверждённого finalize
deploy/vm/build.sh verify     # копия из OVA, проверка, копия остаётся включённой с новым паролем
```

Что важно в шагах:

- **images.** Кроме образов приложения и Ollama сохраняется образ базы. Ссылка на него с версией и дайджестом берётся
  из `docker-compose.yml` подготовленных исходников, архив сохраняется по тегу (например `postgres:17.9-alpine`):
  `docker load` может не сохранить дайджест, поэтому в ВМ образ базы задан тегом в `.env` (`TRIAGE_DB_IMAGE`).
- **data.** База образа строится заново во временном контейнере PostgreSQL того же образа и с теми же настройками базы,
  что у сервиса `db` (контейнер `lt-build-db`, порт на 127.0.0.1, данные в памяти контейнера, случайный пароль только
  в окружении шага; контейнер удаляется в конце шага и при любом отказе). База строится только из демо-данных
  (`demo_db_build.py`); база назначения должна быть пустой, ни одна готовая база (своя папка данных, база прошлого
  прогона) не принимается, переменная `GIVEN_DATA` больше не принимается – шаг отказывает. Новая база собирается кодом приложения: проект «Демо: …» из демо-выгрузки `examples/demo`, путь
  проекта `demo/examples/demo/repos`, ответ SCA из `examples/demo/sca-answers.json`, настройки по умолчанию, адрес
  Ollama `http://ollama:11434`, маленькая модель по умолчанию, новый ключ маскирования. Вердикты демо-находок SAST
  создаёт только прогон большой модели во время этого шага: `demo_db_build.py` ставит прогон всех находок SAST
  в очередь приложения на Ollama этого компьютера (`HOST_OLLAMA`, `BIG_MODEL`). Ollama на компьютере сборки может
  быть занята другой задачей: сценарий ждёт, пока в ней не останется чужих моделей (до 15 минут), сам их
  не выгружает, а после прогона выгружает свою. Если прогон был, вердикты должны быть у всех находок SAST, иначе
  отказ; исходный ответ модели в базе не хранится. `DEMO_VERDICTS=auto` (по умолчанию): модели нет на сервере,
  сервер не отвечает или он занят чужими моделями – образ собирается без вердиктов, демо разбирается при показе
  маленькой моделью в ВМ, в журнале сборки – пометка с причиной; `require` – тогда отказ; `none` – без прогона.
  Состав (`all` или `none`) записывается в `<BUILD>/logs/demo-verdicts`, и все проверки приложения (здесь,
  в `firstboot`, `finalize`, `verify`) ждут именно его. Затем из базы снимается копия `pg_dump -Fc` – файл
  `demo.dump`: мёртвые строки в него не попадают. Все проверки идут на новых базах, восстановленных из этого файла, так
  что заодно проверяется и восстановление. На базе `triage_check` приложение запускается на этом компьютере
  и проверяется: демо-проект с кодом из клонов (с вердиктами или без – по составу), «Создать демо-проект» находит
  клоны (проверочный проект создаётся и удаляется в этой базе, файл не меняется). На базе `triage_final` последняя
  проверка `demo_db_check.py` (только чтение) смотрит состав: ровно один проект «Демо: …», ID находок – из демо-выгрузки,
  ответы модели – только те, на которые ссылается демо-проект, служебные значения и настройки – только известные. Пути
  сборочного компьютера ищутся в содержимом `demo.dump`, развёрнутом в простой текст (`pg_restore -f -`): сам файл
  сжат, и поиск по нему ничего не доказал бы. Состав базы и сведения о вердиктах (источник, модель, число, причина) –
  в `<BUILD>/logs/data-composition.json`. В архив `data.tar.gz` попадает только `demo.dump`: ключ маскирования в нём.
- **iso.** Пароль учётной записи `triage` создаётся один раз в `<BUILD>/secrets/triage-password`, там же ключ
  сборщика `build_ed25519`. Оба файла – вне репозитория; ключ при очистке из ВМ удаляется. Папка `secrets`, пароль
  и ключ – только для владельца: права 600 (700 у папки) и на Windows ACL без наследования с полным доступом одному
  текущему пользователю и без явных прав других (`secret_file.py restrict` перечитывает список: ровно одна
  запись); не удалось ограничить – сборка останавливается. Новый пароль проверочной копии (`first_login.py
  --change`) записывается в новый файл, который сразу создаётся с правами только владельца: наследуемых прав
  каталога у него не бывает, и открыть его другим до записи пароля нельзя (ADR-0039).
  Файл готовится рядом до смены пароля на ВМ и подменяет прежний `triage-password-copy` только после проверки
  входа и `sudo`; если смена или проверка не прошла после отправки нового пароля, подготовленный файл
  `triage-password-copy.new-…` остаётся, а его путь печатается (ADR-0041).
- **install.** Установка ставит обновления, `docker.io`, `docker-compose-v2`, `git`, `ca-certificates`,
  кладёт файлы приложения, данные и модель, настраивает службы. Успех – только если в журнале консоли есть
  завершение установки и штатное выключение.
- **Первая загрузка (`start.sh boot`).** Образы загружаются из архивов, в `.env` записывается случайный
  `POSTGRES_PASSWORD`, если его нет. Том базы есть, а пароля нет – отказ (`db-password-failed`): новый пароль к тому
  не подойдёт. Затем поднимается `db`, сценарий ждёт готовности и, если таблиц в базе нет, восстанавливает
  `data/demo.dump` одной транзакцией (`pg_restore` из образа базы); только после этого запускается приложение. Если
  база не поднялась (`db-failed`) или не восстановилась (`db-restore-failed`), приложение не запускается: оно создало
  бы в пустой базе свою схему, и демо больше не восстановилось бы. Пока подготовка не удалась, в `/opt/local-triage`
  лежит метка `db-pending`: таймер `refresh` повторяет подготовку раз в две минуты и запускает приложение только после
  успеха. Следующие загрузки видят непустую базу и её не трогают. У копии из OVA всё это происходит заново: и пароль,
  и база у каждой копии свои.
- **Ключ SSH сервера и доступ к приложению при сборке.** `start.sh` публикует ключ SSH сервера ВМ через канал
  гипервизора (guestinfo `triage.hostkey`); `build.sh` пишет его в отдельный `<BUILD>/secrets/known_hosts-build`
  (у копии – `known_hosts-copy`) и выполняет SSH только со строгой проверкой ключа. Ответ `ssh-keyscan` по сети –
  лишь перекрёстная проверка: другой ключ на адресе ВМ останавливает сборку (на мостовой сети адрес мог занять
  чужой узел). Приложение в ВМ опубликовано только на 127.0.0.1, поэтому `firstboot` и `finalize` проверяют его
  через SSH-туннель (`ssh_tunnel.py`) и только читают: база образа не меняется. Заодно проверяется, что порт 8765
  из сети не отвечает.
- **finalize.** Кроме проверки приложения: порт приложения в настройках compose – только 127.0.0.1, порт базы
  не опубликован, сеть Ollama закрытая и из контейнера модели нет выхода наружу,
  сценарии VMware Tools при паузе выключены, `git` хранит учётные данные только в памяти. Затем состав ПО
  в `<BUILD>/out/local-triage-demo-packages.txt` и `cleanup.sh`: кэш пакетов, архивы образов, журналы, история,
  ключ сборщика, sudo без пароля, ключи SSH сервера, machine-id, cloud-init; пароль `triage` – к смене при первом
  входе. База прогонов сборки в образ не идёт: таймер `refresh` останавливается на время очистки, контейнеры и том базы
  удаляются (`compose down -v`, в настройках контейнеров записан пароль базы), `POSTGRES_PASSWORD` снимается
  с `.env`, в папке данных остаётся только `demo.dump`; контроль после очистки проверяет именно это.
  В `<BUILD>/logs/vm-config.txt` остаётся пароль базы сборочной ВМ: после очистки в образе его нет, у копии свой.
  Свободное место заполняется нулями. Нули на диске 80 ГБ временно раздувают файл диска сборочной ВМ –
  это нормально, в OVA попадают только занятые блоки. Когда очистка дошла до конца и ВМ выключилась, finalize
  пишет маркер выпуска `<BUILD>/logs/finalized.json`: ревизия, размер и время изменения диска и `.vmx`.
- **export.** Выгружает OVA, только если маркер совпадает с текущим диском и ревизией. Нет маркера (finalize
  не проходил или остановился), ВМ включали после очистки, сменилась ревизия – выгрузки нет: образ с ключом
  сборщика и sudo без пароля не выйдет. Шаги `vm`, `install`, `firstboot` и `finalize` маркер снимают.

## Проверка (verify)

`build.sh verify` разворачивает копию из OVA в `CHECKDIR` так же, как это сделает человек, и проверяет:

1. сеть копии – мост, копия получила адрес по DHCP;
2. ключ SSH сервера копии (из guestinfo, сверен с ответом по сети) и machine-id не совпадают со сборочной ВМ;
3. порт 8765 копии из сети не отвечает: приложение опубликовано только на 127.0.0.1;
4. ключ сборщика копия не принимает (ответ «Permission denied»): сборочного доступа в образе нет;
5. вход по паролю из `secrets` требует сменить пароль;
6. затем пароль копии меняется на случайный – он записывается в `<BUILD>/secrets/triage-password-copy`, в журнал
   не попадает, – и через SSH-туннель по этому паролю: в приложении демо-проект, у всех находок SAST есть
   вердикты (или ни у одной, если образ собран без них); «Создать демо-проект» создаёт проект, у которого `billing-core` и `catalog-api` – «найдена»;
   в нём маленькая модель внутри ВМ разбирает две находки и отвечает на «Спросить модель» (время – в журнале),
   после чего проверочный проект удаляется.

Копия остаётся включённой: вход – `triage` с паролем из `<BUILD>/secrets/triage-password-copy`. Людям
отдаётся OVA, а не эта копия: у развёрнутого из OVA образа пароль из инструкции и требование сменить его.

## Развёртывание и первый запуск

1. Скопировать OVA в папку с латинским путём и сверить SHA256 с файлом `.sha256`.
2. VMware Workstation: File → Open → файл `.ova`, имя и папка ВМ – латиницей. Сеть – Bridged. В ESXi – Deploy
   OVF Template, сеть ВМ – порт-группа с DHCP.
3. Включить ВМ. Через одну-две минуты на консоли ВМ над приглашением входа появится подсказка с адресом ВМ
   и командой SSH-туннеля.
4. Первый вход по SSH: сменить пароль (раздел «Вход в ВМ»).
5. Открыть приложение через SSH-туннель – раздел «Доступ к приложению». Демо-проект – в списке проектов.

## Доступ к приложению

У интерфейса нет входа по паролю и шифрования: любой, кто достучится до порта 8765, читает находки и код
и меняет решения. Поэтому в образе приложение слушает только 127.0.0.1 внутри ВМ.

**Закройте доступ из сети до загрузки настоящей выгрузки и клонирования настоящих репозиториев.** Демо-проект
выдуманный; рабочие данные – нет.

### Способ 1: SSH-туннель (по умолчанию)

На своём компьютере:

```bash
ssh -L 8765:127.0.0.1:8765 triage@<адрес ВМ>
```

Пока сессия открыта, приложение открывается в браузере этого компьютера по адресу http://127.0.0.1:8765/.
Порт 8765 на компьютере должен быть свободен (иначе – например, `-L 18765:127.0.0.1:8765` и адрес
http://127.0.0.1:18765/). Ключ SSH сервера при первом входе сверьте с ключом из консоли ВМ
(`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`) или из guestinfo (`vmrun … guestVar triage.hostkey`).

### Способ 2: доступ по сети с одного адреса

Если туннель неудобен, порт можно открыть на адресе ВМ, но только для адреса пользователя. Важно: правила
`ufw` не действуют на порты, которые публикует Docker, – Docker пишет свои правила в обход цепочек `ufw`.
Ограничение источника для порта приложения ставится в цепочке `DOCKER-USER`, а `ufw` закрывает остальное,
в том числе SSH.

Включается это только сценарием `network-access.sh`, а не отдельными командами: порт публикуется на адресах ВМ
лишь после того, как ограничение установлено и проверено, а при любом отказе приложение возвращается на 127.0.0.1.

```bash
# в ВМ; <адрес пользователя> – IPv4 компьютера, с которого открывают приложение
sudo /opt/local-triage/bin/network-access.sh open <адрес пользователя>
sudo /opt/local-triage/bin/network-access.sh status     # что сейчас: TRIAGE_BIND, адрес, действует ли ограничение, порт
sudo /opt/local-triage/bin/network-access.sh close      # вернуть способ 1 и убрать правило
```

Что делает `open`, по порядку:

1. Переводит приложение на 127.0.0.1 (сначала закрыть, потом открывать) и проверяет это по Docker и по `ss -ltn`:
   контейнер приложения работает и публикует порт только на 127.0.0.1, никакой другой работающий контейнер
   не публикует порт 8765 на другом адресе, на адресах ВМ порт не слушается. Без `userland-proxy` Docker публикует
   порт правилом DNAT без слушающего сокета, поэтому пустой список `ss` сам по себе ничего не доказывает; Docker
   не ответил или контейнер не работает – отказ.
2. Пишет правило в `/etc/ufw/after.rules` между отметками `# local-triage: begin` и `# local-triage: end`
   (повторный запуск заменяет блок, а не дописывает второй): первым правилом цепочки `DOCKER-USER`
   (`-I DOCKER-USER 1`) отбрасываются соединения к порту приложения со всех адресов, кроме адреса пользователя.
   Разрешает SSH только с этого адреса, включает `ufw` и перезагружает его правила.
3. Проверяет по `iptables -S`, что ограничение достижимо: первое правило `DOCKER-USER` – этот `DROP` с
   `! -s <адрес>/32` для порта 8765 (перед ним нет `RETURN` или `ACCEPT`, которые пропустили бы соединение),
   а первое правило `FORWARD` – переход в `DOCKER-USER`. Адрес пользователя записывается в `.env`
   (`TRIAGE_ALLOW`).
4. Только после этого ставит `TRIAGE_BIND=0.0.0.0`, перезапускает приложение и повторяет проверку ограничения
   и публикации порта на всех адресах по данным Docker.

Ошибка любого шага (приложение не перешло на 127.0.0.1, не принято правило `ufw`, `ufw reload` с ошибкой,
ограничение не первое или его нет, перезапуск не удался, порт не опубликован, Docker не ответил, непредвиденная
ошибка команды, прерывание) – `TRIAGE_BIND=127.0.0.1`, перезапуск, проверка, что порт опубликован и слушается
только на 127.0.0.1, и код
возврата 1. Правило ограничения при отказе не снимается: если вернуть приложение на 127.0.0.1 не удалось,
сценарий говорит об этом, а ограничение продолжает действовать. Если правило не первое из-за правил Docker
или `ufw`, доступ по сети не откроется, пока порядок не исправлен (например, перезапуском Docker).

`close` возвращает `TRIAGE_BIND=127.0.0.1`, перезапускает приложение и снимает правило только после того, как
перезапуск удался и Docker подтвердил публикацию порта только на 127.0.0.1 (и порт не слушается на адресах ВМ).
Иначе правило остаётся, код возврата 1: прежний контейнер мог остаться на всех адресах, в том числе без слушающего
сокета. `status` показывает и публикацию по данным Docker, и слушающие сокеты. При каждой загрузке ВМ `start.sh` вызывает `network-access.sh check`: если
`TRIAGE_BIND` не 127.0.0.1, а ограничение для адреса `TRIAGE_ALLOW` не действует (или сценария нет), приложение
остаётся на 127.0.0.1 (в guestinfo – `triage.bind = local-no-guard`). `start.sh refresh` (раз в две минуты) считает
успехом только подтверждённую Docker публикацию порта: после отказа пересоздания контейнера он повторяет попытку на каждом
проходе, а при неподтверждённой публикации возвращает 1 (`triage.bind = unconfirmed`, `triage.status = bind-unconfirmed`)
(ADR-0051); проверка идёт командами `network-access.sh local` и
`public`, которые `start.sh` запускает через `bash` (потерянный исполняемый бит их не отключает). Если сценария нет совсем,
для 127.0.0.1 работает встроенная проверка Docker, а адреса ВМ не подтверждаются: порт возвращается на 127.0.0.1.
Открытый режим допускает ровно одну публикацию порта – на `0.0.0.0`: публикация на `::` или с пустым адресом не
принимается, потому что ограничение источника действует только для IPv4. Когда публикация подтверждена после прежнего
отказа, `start.sh` записывает `triage.bind` и, если приложение отвечает на `/healthz`, возвращает `triage.status = ok`
(не отвечает – `app-not-responding`); отказ `compose` оставляет `triage.bind = unconfirmed` и
`triage.status = compose-failed` (ADR-0057).
Открытый режим, который Docker не подтвердил (в том числе публикация порта на `::`, для которой фильтрации нет), не остаётся:
`start.sh` записывает `TRIAGE_BIND=127.0.0.1`, пересоздаёт контейнер и проверяет закрытие по данным Docker
(`triage.bind = local-unsafe-publication`, `triage.status = bind-reverted`, код возврата 1; следующий проход возвращает
`ok`, а пометка `TRIAGE_NET_NOTE` в `.env` сохраняется до следующих `open` или `close`). Если вернуть порт на 127.0.0.1
не удалось, контейнер приложения останавливается и порт не публикуется (`triage.status = stopped-bind-unconfirmed`; остановка не подтверждена Docker – контейнер работает или сама проверка `docker ps` не удалась – `stop-failed`, повтор при следующем проходе; после подтверждённого восстановления статус возвращается в `ok` только по ответу приложения); отказ первого пересоздания в открытом режиме тоже отзывает открытый режим (0.9.13);
следующий проход поднимает его только на loopback
(ADR-0061). Образ с этими исправлениями не собирался и на настоящей ВМ
не проверялся: правило DNAT без userland-proxy, ВМ с включённым IPv6 и недоступность порта с другого узла не проверены.

Проверка после `open`: с компьютера пользователя открывается http://<адрес ВМ>:8765/, с любого другого – нет
(соединение не устанавливается). Если адрес ВМ сменился (другая сеть, новый DHCP), приложение начнёт принимать
его в течение двух минут. Сценарий проверен на поддельных `ufw`, `iptables`, `systemctl`, `ss` и `docker`
с состоянием, в том числе с отказами перезапуска, чужими правилами перед ограничением, публикацией без сокета,
отказом Docker и посторонним контейнером на том же порту (`tests/test_stage32_review.py`,
`tests/test_stage34_review.py`); на собранном образе – ещё нет.

## Если образ уже развёрнут

Образ версии 0.2.0 (раздел «Текущий образ») собран, когда порт 8765 был открыт на всех адресах ВМ. В такой ВМ
до загрузки настоящей выгрузки переведите приложение на 127.0.0.1 и работайте через SSH-туннель:

```bash
# в ВМ
sudo sed -i 's/^TRIAGE_BIND=.*/TRIAGE_BIND=127.0.0.1/' /opt/local-triage/.env && sudo systemctl restart local-triage
docker port local-triage 8765  # ожидается 127.0.0.1:8765, а не 0.0.0.0:8765 (сокета может не быть – смотрите Docker)
# подсказка на консоли: вместо адреса в сети – команда туннеля
sudo sed -i 's|^Local triage demo: http://\\4:8765/$|Local triage: ssh -L 8765:127.0.0.1:8765 triage@\\4 then http://127.0.0.1:8765/|' /etc/issue
```

С другого компьютера `curl -m 5 http://<адрес ВМ>:8765/healthz` должен завершиться ошибкой соединения, а через
туннель (раздел «Доступ к приложению») приложение открывается. Строку `TRIAGE_BIND` образ 0.2.0 читает из `.env`
так же, как новые образы, поэтому замены файлов не нужно. Если нужен доступ по сети, вместо этого – способ 2.
В образе 0.2.0 сценария `network-access.sh` нет: скопируйте его из репозитория (`deploy/vm/guest/network-access.sh`)
и установите, затем – `open`, как в способе 2:

```bash
# на своём компьютере, из корня репозитория
scp deploy/vm/guest/network-access.sh triage@<адрес ВМ>:
# в ВМ
sudo install -m 755 ~/network-access.sh /opt/local-triage/bin/network-access.sh && rm ~/network-access.sh
```

Проверку правила при загрузке ВМ (`start.sh`) образ 0.2.0 не делает: после перезагрузки такой ВМ проверьте
`network-access.sh status` (строка «ограничение действует») или вернитесь к способу 1 командой `close`.

### Вход в ВМ

В консоли ВМ или по SSH с компьютера в той же сети:

```bash
ssh triage@<адрес ВМ>
```

Пароль – из инструкции к образу. При первом входе система требует сменить пароль: ввести текущий, затем
дважды новый; после этого соединение закрывается, войти снова с новым паролем.

### Клонировать репозитории

Учётные данные git в образе не хранятся. Клонирование – по HTTPS с логином и паролем (или токеном доступа);
`git` держит их в памяти восемь часов (`credential.helper cache --timeout=28800` в `/etc/gitconfig`), на диск
не пишет.

```bash
ssh triage@<адрес ВМ>
cd /srv/repos
mkdir -p <система> && cd <система>          # папка проекта: все кодовые базы одной системы
git clone https://<адрес GitLab>/<группа>/<проект>.git
# логин и пароль (или токен) вводятся один раз за сессию
cd <проект>
git checkout <ветка>                       # та ветка, которую проверял анализатор
```

Если сервер git использует сертификат внутреннего удостоверяющего центра и `git` отвечает
`server certificate verification failed`, проверку не отключать, а добавить корневой сертификат в систему:

```bash
# с компьютера: scp root-ca.crt triage@<адрес ВМ>:/tmp/
sudo cp /tmp/root-ca.crt /usr/local/share/ca-certificates/root-ca.crt   # формат PEM, расширение .crt
sudo update-ca-certificates
```

Какие репозитории клонировать, подскажет само приложение: после загрузки выгрузки на шаге 2 проекта есть список
«Клонировать только эти» – кодовые базы с находками SAST, для которых нет папки, с путём, куда клонировать.
Клон должен лежать внутри `/srv/repos`: только эта папка видна приложению.

## Модель на процессоре и её пределы

В ВМ нет видеокарты, поэтому модель маленькая и работает на процессоре:

- разбор одной находки занимает от одной до нескольких минут, ответ «Спросить модель» – десятки секунд
  (замеры сборки – в журнале `verify`);
- маленькая модель разбирается в коде слабее большой: чаще отвечает «истинная» с высокой уверенностью,
  предлагает неточные исправления. Её вердикты – черновик для человека, а не решение;
- модель `qwen2.5-coder:1.5b` для приложения не годится: её ответ не укладывается в предел длины и обрывается;
- больше ядер ВМ – быстрее разбор: число vCPU можно увеличить в настройках ВМ;
- сейчас приложение разрешает только локальные адреса Ollama (`localhost`, `127.0.0.1`, `::1`,
  `host.docker.internal`, `ollama`). Подключить сервер с видеокартой в сети нельзя – это будущая доработка.

Модель по умолчанию и адрес Ollama видны на странице «Настройки». Другую модель можно загрузить в ВМ, если
у неё есть выход в интернет: `docker exec local-triage-ollama ollama pull <модель>`.

## Обновить приложение в работающей ВМ

Без пересборки образа, данные и клоны сохраняются. На компьютере сборки:

```bash
deploy/vm/build.sh src && deploy/vm/build.sh images     # REV=<новый коммит>
scp <BUILD>/stage/images/local-triage-<версия>.tar.gz triage@<адрес ВМ>:/tmp/
```

В ВМ:

```bash
docker load -i /tmp/local-triage-<версия>.tar.gz
sudo sed -i 's|^TRIAGE_IMAGE=.*|TRIAGE_IMAGE=local-triage:<версия>|' /opt/local-triage/.env
cd /opt/local-triage
docker compose -f docker-compose.yml -f docker-compose.vm.yml exec -T db pg_dump -Fc -U triage -d triage > ~/triage-before-update.dump   # копия базы до обновления
docker compose -f docker-compose.yml -f docker-compose.vm.yml up -d --no-build --pull never
rm /tmp/local-triage-<версия>.tar.gz
```

Схему базы приложение обновляет само при запуске. Этот порядок – для ВМ, где база уже в PostgreSQL. ВМ с базой SQLite
(образы до 0.10.0) так не обновить: там нет сервиса `db`, пароля и тома; путь её перевода не описан и не проверялся.
Если в новой версии изменились `docker-compose.yml`
или `deploy/vm/guest/docker-compose.vm.yml`, их тоже скопировать в `/opt/local-triage/` (через `/tmp` и `sudo cp`);
`TRIAGE_BIND` в `.env` проверить – по умолчанию `127.0.0.1` (раздел «Доступ к приложению»). Состояние после обновления:
`systemctl status local-triage` и `docker ps`.

## Известные проблемы и уроки

- **Пауза ВМ.** Штатный сценарий VMware Tools при паузе стирает адреса всех интерфейсов, в том числе сетей
  Docker, а при пробуждении возвращает адрес только основному адаптеру: приложение перестаёт отвечать. В образе
  эти сценарии выключены (`/etc/vmware-tools/tools.conf`, раздел `[powerops]`). Если всё же не отвечает –
  `sudo systemctl restart docker`.
- **Мост после сна Windows.** Бывало, что после сна компьютера мост VMnet0 не пропускал трафик ВМ; помогала
  холодная перезагрузка компьютера.
- **Имя хоста.** При доступе по сети (способ 2) открыть приложение по имени, которого нет в `TRUSTED_HOSTS`,
  нельзя: ответ «Неверное имя хоста». Через туннель (127.0.0.1) имя хоста всегда разрешено.
  Нужное имя добавить в `/opt/local-triage/.env` через запятую и выполнить `sudo systemctl restart local-triage`.
  `start.sh` при смене адреса перезаписывает строку целиком, поэтому постоянные имена лучше добавить в сценарий.
- **Замок папки данных и часы ВМ.** Приложение держит в папке данных замок `instance.lock` с отметкой времени
  и не запускается, пока отметка свежая. В первой сборке замок остался в образе, а часы сборочной ВМ шли
  по местному времени компьютера (VMware отдаёт ВМ часы в местном времени, Ubuntu считает их UTC): у копии
  отметка оказалась «в будущем», и приложение не запускалось. Теперь `cleanup.sh` удаляет контейнеры
  и замок вместе с остальной папкой данных, кроме `demo.dump` и `mask.key`, `start.sh` при каждой загрузке снимает замок, пока контейнер приложения остановлен (в ВМ
  работает один экземпляр), а в `.vmx` часы ВМ – в UTC (`rtc.diffFromUTC = "0"`).
- **Кириллица в пути** ломает `ovftool` (см. требования).
- **Большие файлы в ISO.** Образ Ollama с библиотеками видеокарт весит больше 9 ГБ; в ВМ он не нужен, поэтому
  собирается свой образ только для процессора (`deploy/vm/ollama-cpu`).
- **Ollama занята.** Вердикты демо готовятся на общей видеокарте: сценарий ждёт до 15 минут, пока чужие модели
  выгрузятся, и выгружает только свою; не дождался – при `DEMO_VERDICTS=auto` образ без вердиктов.
- **База в ВМ.** Смотреть её можно клиентом из образа, не останавливая приложение:
  `docker compose -f docker-compose.yml -f docker-compose.vm.yml exec db psql -U triage -d triage` из `/opt/local-triage`.
- **Маленькие модели.** `qwen2.5-coder:1.5b` обрывает ответ на пределе длины и в разборе не годится; `3b` даёт
  разбираемый ответ.

## Текущий образ

Пересборка с более новой версией – по решению владельца продукта.

В этом образе порт 8765 открыт на всех адресах ВМ, а сценарии сборки ещё без строгой проверки ключа SSH,
проверки состава демо-базы и маркера выпуска: так собирали до исправлений по независимой проверке. Развёрнутую
копию – перевести на 127.0.0.1 по разделу «Если образ уже развёрнут». Изменённые сценарии сборки (`build.sh`,
`start.sh`, `network-access.sh`, `demo_db_build.py`, `demo_db_check.py`, `ssh_tunnel.py`) на ВМ ещё не прогонялись:
первая пересборка их и проверит.

## Что менялось в сценариях ВМ и что открыто

Образ не пересобирался с версии 0.2.0: все исправления ниже проверены на поддельных командах (`docker`, `ip`, `ss`,
`iptables`, `ufw`, `systemctl`, `vmware-rpctool`, `curl`) с состоянием, а не на настоящей ВМ.

Перевод на PostgreSQL (0.10.0, ADR-0128). Шаг `data` прогонялся на компьютере сборки по-настоящему:
временный контейнер базы, `demo.dump`, восстановление, проверка приложением. Подготовка базы из `start.sh` проверена
с настоящим контейнером PostgreSQL вне ВМ и с поддельным `docker`, функции очистки из `cleanup.sh` – только с поддельным
`docker`. Сборка ISO, автоустановка, первая загрузка на настоящей ВМ, `cleanup.sh` целиком, OVA и `verify` не запускались.
В том числе не проверено, загружается ли архив образа базы, сохранённый Docker Desktop, в Docker из пакета `docker.io`
Ubuntu, и хватает ли базе предела памяти `DB_MEM_LIMIT=1g` при настоящей работе в ВМ.


**Открыто:**

- **Критерий «настоящая ВМ»** по замечанию LTA-005: правило DNAT без userland-proxy, ВМ с включённым IPv6, недоступность
  порта с другого узла. Нужна пересборка образа с исправлениями 0.3.12–0.3.21 и проверка на стенде.
- **Два остатка аварийных веток `start.sh`** по повторной независимой проверке версии 0.3.21
  (заключение): отказ самого первого `compose up` выходит до проверки публикации
  и отзыва открытого режима (конфигурация остаётся прежней); результат `compose stop` в `revert_open_mode` не проверяется,
  поэтому статус `stopped-bind-unconfirmed` может быть объявлен без подтверждённой остановки. Исправление и приёмка описаны
  в заключении; до него ВМ нельзя считать подтверждённо закрытой в аварийных ветках.
