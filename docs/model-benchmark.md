# Замер моделей

Стенд в `scripts/bench` ([run_bench.py](../scripts/bench/run_bench.py)) сравнивает модели Ollama на наборе
находок SAST с известными ответами. Каждый случай проходит тот же конвейер, что находка в приложении: срез кода, маскирование, промпт текущей версии,
вызов модели с проверкой ответа и разбор вердикта. По итогам выбирается модель по умолчанию
(ADR-0026).

## Что меряется

- **Качество вердикта:** совпал ли вердикт модели («истинная», «ложная», «неясно») с известным ответом.
- **Надёжность ответа:** сколько ответов не прошли проверку формата или оборвались на пределе длины.
- **Скорость:** время на находку без загрузки модели и скорость генерации (токенов в секунду).
- **Видеопамять:** какая часть модели в видеопамяти и не была ли рядом загружена другая модель.

Стенд не меняет приложение и не пишет в его базу: модули `app/` импортируются только на чтение, ключ маскирования
у стенда свой (`results/bench/mask.key`), поэтому промпты одинаковы для всех моделей.

## Набор

95 случаев:

- **80 тестов OWASP Benchmark (Java)** – восемь категорий: внедрение SQL-кода (`sqli`), команд ОС (`cmdi`), обход
  пути (`pathtraver`), межсайтовый скриптинг (`xss`), внедрение в LDAP (`ldapi`) и XPath (`xpathi`), нарушение
  границы доверия (`trustbound`), слабый генератор случайных чисел (`weakrand`). В каждой категории – первые
  5 настоящих и первые 5 ложных срабатываний по номеру теста, без исключений. Строка срабатывания ищется
  шаблонами по коду метода `doPost` (комментарии и строки не учитываются).
- **15 демо-находок приложения** ([examples/demo/README.md](../examples/demo/README.md), «Какой ответ задуман»):
  10 на Java и 5 на Python; задумано 9 истинных, 5 ложных и одна «неясно». Отдельного источника у находок
  на Python нет: это часть демо.

Ответы для OWASP Benchmark – из его файла ожидаемых результатов, для демо – из таблицы в README демо.

Второй набор – по тестовым проектам с GitHub ([demo-projects.md](demo-projects.md), раздел «Эталон»): OWASP Juice
Shop по авторским меткам уязвимых строк, PyGoat и WebGoat по ручному списку; собирает
[build_cases_projects.py](../scripts/bench/build_cases_projects.py) в `results/bench/cases-projects.json`, прогон –
тем же `run_bench.py --cases …`. У Juice Shop метка стоит в самой строке кода – модель видит подсказку, такие
случаи считаются отдельно (`hint_comment`).

## Как собрать набор

Код и ожидаемые ответы OWASP Benchmark распространяются по лицензии GPL-2.0 и в репозиторий не кладутся. В
репозитории есть только список отобранных тестов – номера и категории, адрес и коммит OWASP Benchmark:
[scripts/bench/owasp-selection.json](../scripts/bench/owasp-selection.json). Набор собирает
[build_cases.py](../scripts/bench/build_cases.py) из клона OWASP Benchmark и демо этого репозитория:

```powershell
# скачать OWASP Benchmark в results/bench/owasp (git clone) и перейти на коммит из списка
.venv\Scripts\python -I -B scripts/bench/build_cases.py --clone

# готовый клон в другой папке (например, перенесённый в закрытый контур)
.venv\Scripts\python -I -B scripts/bench/build_cases.py --owasp ПАПКА_КЛОНА

# только 15 демо-находок, без OWASP Benchmark
.venv\Scripts\python -I -B scripts/bench/build_cases.py --demo-only
```

Результат – `results/bench/cases.json` и `results/bench/cases_meta.json`. Папка `results/` в `.gitignore`: в наборе
есть строки кода OWASP Benchmark и пути к клонам на этом компьютере.

Сборщик проверяет:

- отбор по правилу на ответах клона совпадает со списком из репозитория (иначе – отказ, код 2);
- коммит клона и файл ответов совпадают с теми, на которых отбирался набор (иначе – предупреждение);
- каждый случай проходит через `app.context.build_context` так же, как в приложении, и строка срабатывания
  попадает в срез;
- демо: сценарий `scripts/make_demo_xlsx.py` и выгрузка `demo-hub-report.xlsx` не расходятся, задуманные ответы –
  9 / 5 / 1.

В `cases_meta.json` записываются коммит OWASP Benchmark, хеш файла ответов, итоги проверок и сведения о случаях:
у каких тестов в коде есть подсказки генератора (см. «Ограничения»), какие зависят от кода в другом файле и где
метод `doPost` не целиком попал в срез.

## Модели с hf.co

Часть моделей замера собрана из весов с hf.co или из другой модели Ollama с другим шаблоном диалога. Описание –
[scripts/bench/modelfiles/models.json](../scripts/bench/modelfiles/models.json): источник, оставлять ли проектор
для картинок, `RENDERER`, `PARSER` и параметры. Modelfile готовит
[make_modelfile.py](../scripts/bench/make_modelfile.py) по выводу `ollama show --modelfile`:

```powershell
ollama pull hf.co/ISTA-DASLab/Qwen3.8-27B-GSQ-RCO-GGUF:IQ3_S
.venv\Scripts\python -I -B scripts/bench/make_modelfile.py qwen38-27b-iq3 --create
```

Без `--create` сценарий только пишет `results/bench/modelfiles/<имя>.Modelfile` и печатает команду
`ollama create`. Проектор убирается, чтобы модель занимала столько же видеопамяти, сколько при замере.

## Прогон

[run_bench.py](../scripts/bench/run_bench.py), из корня репозитория:

```powershell
.venv\Scripts\python -I -B scripts/bench/run_bench.py --model gpt-oss:20b --think low
.venv\Scripts\python -I -B scripts/bench/run_bench.py --model gpt-oss:20b --think medium
.venv\Scripts\python -I -B scripts/bench/run_bench.py --model qwen38-27b-iq3 --think false
.venv\Scripts\python -I -B scripts/bench/run_bench.py --model qwen36-a3b-iq3 --think true --num-predict 8192
.venv\Scripts\python -I -B scripts/bench/run_bench.py --model qwen2.5-coder:14b
.venv\Scripts\python -I -B scripts/bench/run_bench.py --model deepseek-r1:14b --num-predict 6144

# без модели: срезы, промпты, оценка размера и проверка маскирования
.venv\Scripts\python -I -B scripts/bench/run_bench.py --model gpt-oss:20b --dry-run --show 100109
```

- **`--think`** – поле `think` запроса к Ollama для любой модели: `low`, `medium`, `high`, `xhigh` – строкой,
  `true`, `false` – логическим значением. Без ключа – как в приложении: моделям gpt-oss уходит `low`, остальным
  поле не передаётся, и рассуждающие модели думают по своему умолчанию. Приложение узнаёт gpt-oss по семейству
  из сведений Ollama (`gptoss` или `gpt-oss`, с версии 0.3.5), а без него – по началу имени.
- **`--num-predict`** – предел длины ответа в токенах. По умолчанию – как в приложении: 3072, не больше четверти
  окна контекста (16384). Рассуждающим моделям с `--think true` его поднимают, иначе ответ обрывается.
- **Отбор:** `--ids`, `--source owasp|demo`, `--category sqli,cmdi`, `--limit N`. Такой прогон в сводке помечается
  неполным.
- **Адрес Ollama** – `--url`; по умолчанию переменная окружения `OLLAMA_URL`, как у приложения, а без неё –
  `http://127.0.0.1:11434`. Разрешённые адреса те же, что у приложения.

Итог – `results/bench/runs/<модель>__think-<режим>__np<предел>.json`, журнал – рядом, с расширением `.jsonl`:
запись на каждый случай сразу после ответа. Прерванный прогон продолжается той же командой; журнал с другой
моделью, режимом или версией промпта не смешивается (код 2, `--restart` начинает заново, прежний журнал
переименовывается).

Видеокарта общая: перед каждым вызовом стенд смотрит `/api/ps` и, если загружена другая модель (или та же с другим
окном контекста), ждёт, пока она выгрузится сама (`--wait-max`, по умолчанию 10 минут). Чужие модели стенд не
выгружает. Ожидание и соседство с чужой моделью записываются в итог.

Коды выхода: 0 – готово; 1 – неверный запуск; 2 – журнал с другими параметрами; 3 – видеокарта не освободилась;
4 – с `--require-loaded` модель не загружена; 5 – Ollama не отвечает; 130 – прервано.

## Метрики

Правило верного ответа одно для всех метрик: вердикт совпал с известным ответом или входит в `also_ok` случая.
`also_ok` – «неясно» там, где по срезу кода ответить нельзя: у тестов OWASP Benchmark, где значение берётся из
метода в другом файле (BenchmarkTest00051, BenchmarkTest00052), и у демо-находок, где README допускает «неясно»
(100102). Случай без разобранного ответа (не по формату, оборван, сбой сервера, нет кода) считается неверным.

| Метрика | Как считается |
|---|---|
| Точность полного конвейера | верные / все случаи с известным ответом; неразобранные ответы – неверные |
| Настоящие найдены | верные среди настоящих срабатываний (чувствительность) |
| Ложные распознаны | верные среди ложных срабатываний (специфичность) |
| Пропуски настоящих | настоящая находка названа ложной – самая опасная ошибка |
| Ложная названа настоящей | лишняя работа человека |
| «Неясно» | доля ответов «неясно» среди разобранных |
| Уверенность на ошибках | средняя уверенность модели в разобранных неверных ответах |
| Время на находку | медиана и среднее без загрузки модели в память |
| ток/с | все токены ответа, делённые на всё время генерации |
| Не разобрано, оборвано | ответы, отвергнутые проверкой формата; из них упёршиеся в `num_predict` |

Проценты в сводке считаются из целых чисел (половина округляется вверх), рядом – дробь «верно / всего».

## Сводка

```powershell
.venv\Scripts\python -I -B scripts/bench/summary.py --out results/bench/summary.md
```

[summary.py](../scripts/bench/summary.py) читает все итоги из `results/bench/runs` (вложенные папки – нет) и строит
таблицы Markdown: сводку по местам, по источнику (OWASP с подсказками генератора и без, демо) и по категориям.
Порядок: полные прогоны по точности, при равной – меньше пропусков настоящих, затем быстрее; неполные – в конце
со звёздочкой. В примечаниях – предупреждения, если итоги собраны разными версиями промпта, приложения или набора
и если часть модели была в памяти процессора.

## Внешний провайдер и sast-v7

Замер на внешнем провайдере по API чат-завершений – [run_bench_remote.py](../scripts/bench/run_bench_remote.py)
(В7, ADR-0109). Это платные запросы с ключом владельца – их
запускает владелец. Ключ – только из переменной окружения (`--key-env`), из папки данных приложения стенд его не
читает; без `LLM_EXTERNAL=1` запрос не уходит; вне контейнера действуют все проверки адреса приложения.

```powershell
$env:LLM_EXTERNAL = '1'; $env:DEEPSEEK_API_KEY = '<ключ>'
$out = '<папка для итогов вне репозитория>'
$common = '--url', 'https://api.deepseek.com', '--key-env', 'DEEPSEEK_API_KEY', '--model', 'deepseek-v4-pro',
          '--thinking', 'enabled', '--effort', 'high', '--max-output', '65536', '--context-window', '1000000'
# набор 95 случаев (results/bench/cases.json)
.venv\Scripts\python -I -B scripts/bench/run_bench_remote.py @common --prompt-version sast-v6 --out "$out\v6-95.json"
.venv\Scripts\python -I -B scripts/bench/run_bench_remote.py @common --prompt-version sast-v7 --out "$out\v7-95.json"
# набор тестовых проектов (results/bench/cases-projects.json)
.venv\Scripts\python -I -B scripts/bench/run_bench_remote.py @common --prompt-version sast-v6 --cases results/bench/cases-projects.json --out "$out\v6-projects.json"
.venv\Scripts\python -I -B scripts/bench/run_bench_remote.py @common --prompt-version sast-v7 --cases results/bench/cases-projects.json --out "$out\v7-projects.json"
# сравнение
.venv\Scripts\python -I -B scripts/bench/compare_runs.py "$out\v6-95.json" "$out\v7-95.json" --out "$out\v6-v7-95.md"
.venv\Scripts\python -I -B scripts/bench/compare_runs.py "$out\v6-projects.json" "$out\v7-projects.json" --out "$out\v6-v7-projects.md"
```

- Подготовка случая – та же, что у прогона с удалённым исполнителем: окно и предел ответа профиля за вычетом схемы
  ответа, длина – по JSON сообщений, наименьший срез тоже пробуется.
- Журнал – каждая HTTP-отправка отдельно: «попытка начата» до отправки (не записалась – отправки нет), «ответ
  получен» (`finish_reason`, `usage` как в ответе) или «ошибка». Расход – сумма ответов всех попыток. Случай с
  неизвестным исходом (обрыв после отправки, 502, 504; прерывание между отправкой и записью) при продолжении не
  отправляется – запрос мог быть принят и оплачен; повтор – `--resend-unknown`.
- Остановка: 401 и 403 – код 6 (ключ), 402 – код 7 (баланс), отказ допуска – код 1; другие ошибки – ошибка случая.
- В итоге – таблица случаев (хеш показанного кода, статус, вердикт, цитаты), отпечатки набора, ключа маскирования
  стенда, реализации, модели, адреса и параметров. `compare_runs.py` проверяет, что различается только версия
  промпта, и считает попарные переходы, «код тот же / срез меньше / код другой».
- Метрики цитат sast-v7: доля цитат, найденных в коде (`exact` и `normalized` среди принятых), доля ответов хотя бы
  с одной найденной, ответы без цитат, отброшенные (повторы и сверх пяти), доля ответов с «не хватило кода».

## Замер 08.11.2026: qwen3-coder:30b против модели по умолчанию

Вопрос: не лучше ли для триажа модель с пометкой «кодер». Прогон `qwen3-coder:30b` на тех же 95 случаях,
промпт sast-v6, параметры как в приложении (поле think не передаётся, предел ответа 3072, окно 16384); эталон – итог
`results/bench/runs/adr79-v6-base` (gpt-oss:20b, рассуждение low, тот же промпт; версия приложения 0.8.0 – сравнение с

`scripts/bench/summary.py --results`.

| Модель | Точность | Настоящие найдены | Ложные распознаны | Настоящая названа ложной | Ложная названа настоящей | Уверенность на ошибках | Время на находку | ток/с | Видеопамять |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---|
| gpt-oss:20b, low | 80,0 % (76/95) | 47/49 | 28/45 | 2 | 17 | 93 | 3,8 с | 173 | 11,9 ГиБ, целиком |
| qwen3-coder:30b | 63,2 % (60/95) | 49/49 | 10/45 | 0 | 35 | 95 | 11,7 с | 68 | 13,5 из 19,1 ГиБ, часть на процессоре |

На OWASP с подсказками генератора (там сосредоточены ложные срабатывания): gpt-oss:20b – 67,6 % (25/37), qwen3-coder:30b –
24,3 % (9/37); без подсказок – 88,4 % и 90,7 %. Кодер не пропускает настоящие находки, но подтверждает 35 из 45 ложных
срабатываний с уверенностью 95: для оператора это лишние разборы. Вывод тот же, что 15.10 для qwen2.5-coder:14b: модели с
пометкой «кодер» для триажа уступают рассуждающей модели по распознаванию ложных срабатываний. Модель по умолчанию не
меняется.

## Замер 09.11.2026: метки секретов в находках о паролях (бэклог 101)

Вопрос: модель приняла метку маскирования `<SECRET_…>` за сам секрет. Стенд без правки
приложения: локальный `run_bench.py` получил `--prompt-version`, `--mask-shape` (метка с формой исходного значения
`<SECRET_xxxxxx len=N chars=hex|alnum|mixed>` после маскирования; форма – по значению, которое закрыло
маскирование приложения) и `--secret-note` (оговорка в системном сообщении:
метка – маскирование приложения, не само значение). Набор – 12 выдуманных случаев CWE-259/CWE-798
([secret_cases.py](../scripts/bench/secret_cases.py), `build_cases.py --demo-only --secrets`): 5 настоящих, 6 ложных,
1 задуманный «неясно». Модель gpt-oss:20b, рассуждение low, параметры как в приложении; по одному прогону на
конфигурацию. В конфигурации 2 после исправления формы метки (ревью стенда) запрос изменился у одного случая, он
разобран заново; у остальных 11 запрос тот же, записи журнала действуют.

| Конфигурация | Верно из 11 | Ложная названа настоящей | Настоящая названа ложной | Время на находку |
|---|---:|---:|---:|---:|
| 1. sast-v6, контроль | 6 | 5 | 0 | 2,9 с |
| 2. sast-v6, `--mask-shape` | 7 | 4 | 0 | 3,0 с |
| 3. sast-v7, контроль | 6 | 5 | 0 | 3,3 с |
| 4. sast-v7, `--secret-note` | 8 | 3 | 0 | 3,5 с |

Случай с задуманным «неясно» (пароль тестового пользователя в фикстуре) во всех конфигурациях получил «истинная» и в счёт
не входит. Настоящие все пять найдены везде, ошибки – только в сторону «ложное названо настоящим», с уверенностью 90–100.

Что видно по случаям:

- Пустая строка при выходе (`{accessToken: ''}`) в текущей версии не маскируется, но модель всё равно ставит «истинная»:
  в том же срезе выше строка `state.accessToken = accessToken` показана как `state.accessToken = <SECRET_…>` –
  маскирование закрывает меткой и правую часть присваивания без кавычек. Модель читает это как постоянное значение в коде
  («токен задаётся напрямую из строки, заменённой меткой»). Форма метки здесь не помогает: и с меткой
  `<SECRET_… len=11 chars=alnum>` ответ тот же.
- Подпись поля формы (`"Пароль"`) и имя ключа хранилища модель называет паролем во всех четырёх конфигурациях.
- В случае с фикстурой оба аргумента вызова закрыты метками (`login="<SECRET_…>", password="<SECRET_…>"`), модель
  всё равно называет находку настоящей. Пометка «секрет в промпте ОТКРЫТ» в пробном показе стенда здесь ложная: проверка
  ищет в промпте любую строку из кавычек строки срабатывания от четырёх знаков, а «demo» есть в имени функции.
- Оговорка о метке исправила два случая из шести ложных (чтение из переменной окружения и имя параметра настроек), форма
  метки – один (переменная окружения).

Разница между конфигурациями – один-два случая из 11 на одном прогоне: для переноса в приложение этого мало. Дополнительный прогон 09.11 утром – sast-v6 с той же оговоркой: 8 из 11 верно, ложное названо настоящим – 3, настоящие найдены все. Оговорка перенесена в приложение – промпт sast-v8 (ADR-0148). Стенд без флагов воспроизводит сообщения текущей версии приложения
(`tests/test_bench_secret_shape.py`); форма метки и метка на правой части присваивания без кавычек не менялись – решение о них –
слово владельца по числам (ADR-0118, бэклог 80).

## Ограничения

- **Синтетика.** OWASP Benchmark и демо – учебные примеры, а не код рабочих систем: точность на настоящих находках
  может отличаться. Набор с известными ответами по настоящим отчётам остаётся задачей.
- **Подсказки генератора.** В части тестов OWASP Benchmark есть комментарии, прямо говорящие, безопасен ли поток
  данных. Модель их видит, поэтому сводка показывает точность отдельно на тестах с подсказками и без.
- **Один прогон.** У моделей с выборкой при ненулевой температуре ответы разнятся от прогона к прогону; разница
  в 1–2 случая между моделями – в пределах разброса.
- **Версия приложения.** В итоге записываются версия приложения, версия промпта и отпечаток модулей конвейера;
  итоги разных версий сравниваются с оговоркой (сводка предупреждает).
- **Окно кода.** Модель видит срез вокруг строки срабатывания, как в приложении; код в других файлах и часть
  длинных методов в срез не попадают (`cases_meta.json`).
- **Скорость** зависит от видеокарты и от других моделей в Ollama; время ответов рядом с чужой моделью ненадёжно.

## Результаты 15.10.2026

Условия: видеокарта NVIDIA RTX 5080 (16 ГиБ), Ollama 0.40.4, окно контекста 16384, промпт `sast-v3`, набор
из 95 случаев (49 настоящих, 45 ложных, один «неясно»). Каждая модель целиком в видеопамяти; при ожидании
чужой модели время ожидания в замер не входит.

### Первичный замер – десять конфигураций

Отбор кандидатов. Прогоны шли, пока дорабатывался конвейер, поэтому версии приложения у них разные и сравнение –
с оговоркой. Четыре лучшие конфигурации дали 80–82 %. Остальные заметно слабее: gemma4:12b и qwen2.5-coder:14b
(прежняя модель по умолчанию) – по 64,2 %, deepseek-r1:14b – 60,0 %, qwen36-a3b-iq3 без рассуждения – 58,9 %,
qwen3.5:9b – 56,8 %, ornith-1.5-9b – 45,3 %. Почти все они часто называют ложные срабатывания настоящими:
qwen2.5-coder:14b распознала 13 ложных из 45, qwen3.5:9b – 10 из 45. gemma4-26b в проверенной конфигурации
(без поля think, предел ответа 3072) не дала ни одного разобранного ответа на первых 19 случаях – все ответы
оборвались на пределе длины, прогон остановлен.

### Вывод

- Модель по умолчанию – gpt-oss:20b с рассуждением low (ADR-0026).
  Превосходство по качеству не установлено: разница в точности между четырьмя конфигурациями – 1–2 случая, в пределах
  разброса одного прогона (qwen36-a3b-iq3 с рассуждением дала 80,0 % в первичном замере и 82,1 % в повторном).
  Выбор – по скорости при равной точности и малом числе пропусков настоящих; ответы не обрываются.
- Запасные: qwen38-27b-iq3 без рассуждения – ни одного пропуска настоящих, но 18 ложных из 45 названы настоящими
  и около 14 с на находку; qwen36-a3b-iq3 с рассуждением – та же точность, около 30 с на находку.
- Приложение передаёт поле think только моделям gpt-oss и держит предел ответа 3072: параметры замера запасных
  конфигураций в приложении сейчас не воспроизводятся. Настройка режима рассуждения и предела ответа для модели –
  в плане доработок.
