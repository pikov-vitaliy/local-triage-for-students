# Формат AppSec.Hub: выгрузка, дефекты и сценарий работы

Справка для разработчиков приложения: что приходит из AppSec.Hub, что пользователь вставляет обратно и в каком порядке он работает. Примеры ниже выдуманные.

## Сценарий работы пользователя

1. Выгружает из AppSec.Hub Excel-отчёт по приложению.
2. Клонирует на компьютер репозитории, на которые ссылается отчёт (приложение показывает список «клонировать только эти»). Клонирование – по HTTPS с логином и паролем или токеном.
3. В приложении задаёт проект: отчёт, папку с клонами, модель – и запускает разбор SAST.
4. Приложение берёт уязвимый код с запасом из файла (путь и строка – из отчёта), разбирает находку локальной моделью и обогащает сведения из справочников (БДУ ФСТЭК России, CWE, CVE).
5. Пользователь выносит решение. SAST – одно из двух (ADR-0089): «Ложное срабатывание» – меняет статус находки в Hub и вставляет короткий комментарий; «Подтверждаю дефект» – отмечает в AppSec.Hub галочкой эту находку и находки её подгруппы – та же строка, та же категория и одинаковый код (в группе, слившейся при обновлении приложения с разными номерами, – только находки этого дефекта), создаёт из них дефект, вставляет из приложения **заголовок** и **тело**, сохраняет и идёт к следующей находке; статус находок не меняет.
6. По SCA приложение готовит пакет для внешних агентов (только библиотеки, версии и идентификаторы уязвимостей); агентов запускает пользователь, ответы загружает обратно.

**Запись в Hub из приложения.** Шаги 5 и 6 переходят из рук в запросы: приложение ставит операцию в
очередь, исполнитель там, где виден Hub, выполняет её под сессией оператора. В 0.9.20 – очередь, исполнитель и
«Проверить связь»; в 0.9.21 – «Ложное срабатывание» и «Риск принят» (статус, комментарий, срок действия) одним
запросом на находку или группу; в 0.9.22 – дефект из отмеченных находок по заготовке Hub и вкладка «Дефекты».
Копирование текстов для ручного переноса остаётся.

**Статус из карточки (0.9.21, ADR-0115).** В Hub уходит то же, что оператор
переносил руками: `status` – машинное значение (`False Positive` для «Ложного срабатывания», `Accepted risk` для
«Риска принят»; русские подписи статусов в настройках – только для текста), `reason` – короткий комментарий из
предпросмотра, `expiredAt` – срок действия статуса, выбранный оператором (начало дня по UTC, `ГГГГ-ММ-ДДT00:00:00Z`).
Hub принимает этот вид и хранит срок как **конец того же дня по UTC**
(`ГГГГ-ММ-ДДT23:59:59Z`); «Дата окончания» в интерфейсе Hub показана в часовом поясе браузера – при сроке 26.01 в
часовом поясе UTC+3 это 27.01, 02:59:59. Статус действует весь выбранный день; сверка срока в приложении – по дню UTC,
поэтому совпадает.
Одна находка – `POST /issue/status/update` с `issueId` и `issueType` (`SAST`, `SCA_S`); группа SAST «та же строка,
категория и код» с тем же решением и текстом – `POST /issue/status/change` со списком `issues`; соседи, уже внесённые
в Hub, в группу не входят: тот же статус повторно Hub не ставит и отклоняет весь запрос (400, `errorMessage` «issue
already has the requested status», ADR-0116); «уже внесена» решает последняя
принятая версия находки – «Pull из Hub» или подтверждённая запись приложения (уточнение ADR-0116 от 01.11). Ошибку Hub отдаёт по своей
схеме: `errorMessage` и `requestValidationError`.
Комментарий у статуса, который уже стоит, Hub отдельно не меняет: замена – двумя записями, промежуточный статус
`Confirmed` со служебным пояснением и прежний статус с новым `reason`, по подтверждению оператора («Обновить
комментарий в Hub», 0.9.26.dev29, ADR-0130). `To verify` через
`POST /issue/status/update` Hub не ставит: ответ Hub – 400 `To verify is not available for status change`
(0.9.26.dev31).
Находка, входящая в дефект, статус отдельно не получает: в составе дефекта Hub держит только находки со статусом
Open, поэтому статус и комментарий у неё идут через дефект (ADR-0131, 0.9.26.dev32).
Несколько находок SAST из разных строк – «Отправить выбранные в Hub» из списка
(ADR-0119): один `POST /issue/status/change` с общим комментарием оператора и
сроком; сохранённые решения не меняются, отметка хранит отпечаток общего текста. Отметка «Внесено в
Hub» ставится по ответу Hub; «результат неизвестен» сверяется чтением `GET /issue/status?issueId&issueType`.

Ветка и коммит клона в текст дефекта не нужны: сведения об объекте сканирования даёт блок Hub («Информация об объекте
сканирования» по шаблону Hub) – из заготовки при создании и из описания Hub у существующего дефекта. С 0.9.26.dev30 он
часть текста дефекта в приложении: карточка показывает его под текстом команды, создание и «Push в Hub» отправляют
текст и блок (с 0.9.26.dev4 по dev29 в Hub уходил только текст).

**Дефект через API (0.9.22, ADR-0120).** Заготовка – `GET
/defects/blank?appId&issueIds&type` по всем находкам группы или набора (`issueIds` через запятую): `DefectDto` без
`id` – `summary`, `description` (HTML, блок «Информация об объекте сканирования»), `priority` и `severity`
`{name, rank}`, `source`, `stage`, `type`, `status`, `linkedIssues`. Создание – `POST /defects` с той же заготовкой и
правками: `appId`, `summary` – заголовок приложения `ID<n> - …`, `description` – текст команды в HTML (абзацы `<p>`,
строки `<br>`, пункты «1)», «2)» – текстом в строках с 0.9.26.dev14, без стилей и скриптов) и следом `description` заготовки как есть,
`priority` и `severity` – из заготовки или из справочника `GET /defects/serviceInfo` (`statuses`, `priorities`;
серьёзности справочник может не дать). Номер дефекта – из тела ответа (`id`) или `Location`, подтверждается чтением
`GET /defects/{id}`: в `linkedIssues` должны быть все находки; иначе один `POST /defects/{id}/link`
(`{defectId, issueIds, issueType, groupId}`) и чтение снова. Статусы находок не меняются. Ответ на `POST` не
пришёл – сверка по `GET /defects?appId&pageIndex&pageSize` (`filteredEntities`, `totalEntitiesCount`): тот же
`summary`, тот же автор, те же находки и текст команды в начале `description`.

## Выгрузка: листы и колонки

Книга Excel, все значения – строки, пустое значение – «-».

| Лист | Колонки |
|---|---|
| Summary Report | Application; сводка по критичности (Critical, High, Medium, Low) и по практикам |
| SAST | Issue id, Application, Severity, Category, File, Line number, Source code, Status, Type, Found By, CWE ID, CWE link, Codebase, Artifact, Language |
| SCA Security | Issue id, Application, Severity, CVSS score, Category, Component name, Component version, CVE id, Status, Type, Found By, Non-vulnerable versions, Path, CWE ID, CWE link, Codebase, Artifact, Proxy |
| SCA Compliance | Issue id, Application, Severity, Category, Component name, Component version, Licenses, Status, Type, Found By, Non-vulnerable versions, Path, Codebase, Artifact, Proxy |
| DAST | Issue id, Application, Severity, Location, Source, Status, Found By, CWE ID, CWE link, Artifact, Instance |

Особенности:

- **SAST.** `File` – путь от корня кодовой базы, `Line number` – строка срабатывания, `Source code` – одна строка кода с хвостом « : N» (номер строки). `Category` – название правила по-русски, оно же идёт в заголовок дефекта. `Found By` – анализатор (например, `appinspector`).
- **Код с запасом.** По `Codebase` и `File` приложение находит файл в клоне и берёт срез вокруг `Line number` и объемлющий метод; строку из `Source code` сверяет с клоном. Без клона модель видит только строку из `Source code`.
- **SCA.** В колонке `CVE id` наблюдались и публичные идентификаторы (CVE, GHSA, NVD, BDU), и внутренние номера вида `AST-2026-123456`; приложение принимает оба вида и сохраняет номер как есть. Внутренние номера идентификаторами CVE не являются, и соответствие AST → CVE в план работ не входит: формат выгрузки мы не ждём, API Hub не исследуем, а нового плана по будущей выгрузке Hub не строим (план доработок, п. 13 снят). Что известно о номерах AST – [ast-identifiers.md](ast-identifiers.md). `Non-vulnerable versions` – версия исправления. `CWE ID` бывает списком («1333, 400»).
- **Severity у SCA** – уровень политики Hub, а не тяжесть уязвимости (Critical при CVSS 7,5); срочность считается по `CVSS score`.
- **Статус** в выгрузке – английский (`To verify` и др.); в интерфейсе Hub статусы русские (ниже).
- Хвост листа может содержать пустые строки до 1 048 576 – их нужно пропускать.
- **Ссылки-формулы.** Настоящая выгрузка хранит `Issue id`, `Application` (листы SAST и SCA Security), `CVE id` (SCA Security, там идентификаторы AST) и название системы в ячейке B3 листа Summary Report не значениями, а формулами `HYPERLINK("адрес в Hub","видимый текст")` с сохранённым значением, равным видимому тексту. Значение хранится строкой (`t="str"`, так в обезличенном файле) или как индекс общей строки (`t="s"`, так в настоящих полных выгрузках: во всех ячейках колонок A и B листа SAST и колонок A, B и H листа SCA Security); для `t="s"` общая строка должна быть простой (одна `<t>`, без rich text и фонетики) и совпадать с видимым текстом. Такие формулы принимаются, и только в этих полях: значение ячейки – видимый текст, адрес не сохраняется (в `File`, `Line number`, `Source code`, `Component name`, `Path` и других ссылка – такая же формула, как любая, то есть отказ). Любая другая формула в колонках, из которых берутся сведения о находках, по-прежнему отказ, в прочих колонках – предупреждение (ADR-0043, ADR-0044, ADR-0048, ADR-0052, ADR-0053, ADR-0062). Принятые ссылки одной колонки подряд считаются одним участком формул, поэтому полная выгрузка (тысячи ссылок) пределов числа участков не достигает.
- В `Source code` у SAST – одна строка кода с хвостом « : N»; в сводке числа по практикам и критичности могут быть больше числа строк в обезличенной или урезанной выгрузке: тогда сверка со сводкой даёт предупреждение, а не отказ.

## Статусы уязвимости в Hub

«Не подтверждено», «Подтверждено», «Открыто», «Исправлено», «Ложное срабатывание», «Риск принят».

**SAST с 0.9.6** (ADR-0089) – два решения. «Ложное срабатывание» – статус
«Ложное срабатывание» и короткий комментарий оператора. «Подтверждаю дефект» – дефект из отмеченных находок, статус
находок не меняется. «Отложить» – в Hub ничего не переносится. Таблица ниже – соответствие итогов статусам Hub и
ГОСТ. Для SCA с 0.9.8 (ADR-0091 п. 3) исход «Обновить» оформляется
дефектом набора после сохранения его текста, статус находок в Hub при этом не меняется; «Ложное срабатывание» и
«Риск принят» – комментарием и сменой статуса. Для SAST дефект – только при «Подтверждаю дефект», тоже без смены
статуса; строки «Риск принят» и «неясно» для SAST относятся к решениям до 0.9.6. Колонка «Статус в Hub» строки
«истинная, «обновить»» – соответствие по ГОСТ, а не указание сменить статус.

| Итог разбора | Статус в Hub | SAST (ГОСТ Р 71207-2024, п. 5.5) | SCA (ГОСТ Р КАПО, пп. 6.12, 6.14) |
|---|---|---|---|
| истинная, «обновить» | Подтверждено | истинное срабатывание: ошибка в программе, требуется исправление | уязвимость актуальна или анализ не завершён: требуется обновление или обоснование неактуальности |
| ложная, «не применимо» | Ложное срабатывание | ложное срабатывание | ложноположительное: компонент или сведения об уязвимости определены ошибочно |
| решение человека | Риск принят | истинное срабатывание, не требующее исправлений кода; обоснование и условие пересмотра обязательны | уязвимость неактуальна (с обоснованием) или нейтрализована принятыми мерами |
| неясно, «Отложить» | статус не менять (Не подтверждено) | решение не принято | решение не принято |

«Открыто» и «Исправлено» – жизненный цикл, при триаже не выбираются. Подсказки соответствия ГОСТ видны в карточке SCA
(список итога и легенда) и на странице «Настройки» (ADR-0085); в карточке SAST
с 0.9.6 – легенда двух решений.

**Уточнение SCA по ГОСТ Р КАПО** (`kapo_state`): для «Подтверждено» – «анализ не завершён» (по умолчанию) или
«актуальна»; для «Риск принят» – «неактуальна для продукта» или «нейтрализована принятыми мерами», выбор обязателен;
«Ложное срабатывание» – «ложноположительное срабатывание» автоматически. У решений до 0.9.0 уточнения нет: для
«Подтверждено» текст пишется как «анализ не завершён».

## Короткий текст «Скопировать короткий текст для Hub»

Образцы на выдуманных данных, как их выдаёт приложение.

SAST (с 0.9.6) – только для ложного срабатывания, обоснование оператора как есть (с 0.9.11 первая буква –
заглавная, если обоснование начинается со строчной русской буквы; ADR-0101 п. 7), одна-две фразы:

```
Имя таблицы берётся из заранее заданной строки, поэтому SQL-инъекция исключена.
```

Статус «Ложное срабатывание» выбирается в Hub списком, в комментарий он не пишется. Для подтверждённой находки
короткого текста нет – только дефект.

SCA (с 0.9.11, ADR-0101 п. 2) – только для «Ложное
срабатывание» и «Риск принят»: «<публичные идентификаторы находки> в <компонент> <версия>: <обоснование оператора>»
(без «Статус: …», заключения по ГОСТ Р КАПО и требований к разработчику). Идентификаторы – CVE, GHSA, БДУ находки и её
известные публичные соответствия; внутренних номеров AST в тексте нет; публичных нет – «<компонент> <версия>: …»;
обоснование уже начинается с номера – приставки нет. Для «Обновить» короткого текста нет: статус находок в Hub не
меняется, создаётся дефект набора (ниже). Образец для «Риск принят»:

```
CVE-2021-23337 в lodash 4.17.20: функция template не используется, шаблоны не приходят извне – уязвимость неактуальна для продукта.
```

Длиннее 250 знаков – предупреждение у поля (в списке Hub комментарий обрежется), сохранение не запрещается. Это предел короткого комментария к статусу находки: ложное срабатывание и риск принят. Описание дефекта им не ограничено.
Прежние форматы – 0.9.0–0.9.7 («Статус: …», «Комментарий: …» с заключением по ГОСТ Р КАПО) и 0.9.8–0.9.10 (только
обоснование) – приложение помнит для узнавания отметок «Внесено в Hub» («формат обновился»).

## Дефект: заголовок

- SAST: `ID<n> - <Category> (SAST)`, например `ID38 - Изменение произвольных файлов (SAST)`.
- SCA: `ID<n> - <Component name> | Component version: <Component version> (SCA)`, например `ID1 - lodash | Component version: 4.17.21 (SCA)`.
- `ID<n>` – сквозной номер дефекта приложения в Hub (не Issue id и не номер дефекта `#nnnn`); его вводит пользователь или приложение предлагает следующий по счётчику проекта.
- Один дефект SCA – на набор находок одной версии компонента с исходом «Обновить» (по умолчанию – все такие находки версии, из любых объектов сканирования); находку можно вынести в отдельный дефект со своим номером или отметить «без дефекта» с обоснованием (ADR-0091).

Если номер остался у находки SAST после прежней выдачи текста, кнопка «Снять номер ID<n>» появляется в шаге 6 при
сохранённом решении «Ложное срабатывание» – при условии, что с находкой не связан дефект приложения. Нажмите её:
приложение повторно проверит показанный номер, решение и отсутствие связи с дефектом; при несовпадении ничего не
изменит. Если номер остаётся у других ключей, он снимается только у этой находки, а ответ называет оставшихся
держателей. Когда сосед по группе с решением «Подтверждаю дефект» держит тот же номер, сначала разберитесь с
соседом: его номер – номер группы, поэтому предупреждение у занесённого дефекта остаётся. Если других держателей
нет, у занесённого дефекта нажмите «Сверить с Hub» → «Применить», чтобы снять предупреждение о занятом номере
перед подготовкой обновления.

## Дефект: тело

**SAST** (с 0.9.6, ADR-0089) – только для решения «Подтверждаю
дефект», классическая структура команды и ничего больше: ни внутренних номеров Hub, ни требований ГОСТ к конвейеру,
ни срока, ни справки CWE. Название команды – настройка приложения; обоснование и рекомендация – оператора:
поле «Рекомендация» само не заполняется, оператор пишет пункты или явно нажимает «Взять пункты из рекомендации
модели», проверяет их и сохраняет решение. Без сохранённой рекомендации дефект не выдаётся. Если определить статус по коду нельзя, находка откладывается:
дефект не создаётся. Образец:

```
После тщательного анализа уязвимости команда Платформа приняла решение присвоить данной уязвимости категорию True Positive.

Обоснование:
Строка 42 подставляет параметр owner из запроса в SQL-запрос конкатенацией, без параметризации: через него можно изменить запрос и прочитать чужие данные.

Рекомендация:
1) Использовать параметризованные запросы PreparedStatement.
2) Для динамических частей SQL (имя таблицы, колонки, ORDER BY) – белый список или заранее заданные шаблоны запросов.
```

Один дефект – для подгруппы находок, сработавших на той же строке в той же категории с одинаковым кодом вокруг
строки срабатывания, в том числе из других коммитов и кодовых баз
(ADR-0092): карточка показывает их и предлагает тот же
номер дефекта, в Hub дефект создаётся сразу из всех этих находок. Находка той же строки и категории с другим кодом
допускает отдельное решение. Если после обновления приложения в объединённой группе сохранились разные номера
(ADR-0095), сверьте в Hub принадлежность находок и сохраните
соответствующие номера: автоматически они не сводятся.

Дальше Hub сам добавляет блок «Информация об объекте сканирования: / Сводка по уязвимостям: / Детальная информация по уязвимостям:» (ID, файл и строка, серьёзность, категория, дата сканирования, объект, ветка, коммит, URL, трасса, описание анализатора, категории OWASP, PCI DSS, NIST).

**SCA** (с 0.9.8, ADR-0091,
ADR-0094) – дефект по шаблону команды из
текста набора, четыре раздела и ничего больше: «Описание» – уязвимости набора с публичным идентификатором, каждая со ссылкой
(NVD для CVE, GitHub для GHSA, БДУ ФСТЭК России для BDU): сначала найденные Hub в находках набора, затем строка «Также
затрагивают эту версию:» и применимые по исследованию, которых Hub не нашёл; внутренних номеров AST в тексте нет –
уязвимость только с AST в текст не входит (ADR-0101 пп. 1, 3);
«Объяснение» – строки оператора
«идентификатор: что это и при каких условиях срабатывает» (заготовка – из БДУ по CVE, исследования компонента или
ответа агента; текст проверяет и сохраняет человек); «Рекомендации» – строки об остаточном риске (уязвимость без
исправления: слова по статусу, дата и источник доказательства, важность по CVSS), пояснение «почему не версия Hub»
(только когда исследование доказало, что цель не затронута), добавление оператора и «Обновление <компонент> до
версии <цель>»; «Источники» – ссылки уязвимостей и первоисточники исследования (бюллетени, заметки о релизах,
трекеры). Целевая версия – по основанию: ввод оператора, решение по компоненту, совет исследования, ответ агента;
её проверка по диапазонам – в карточке, выдача без проверенной версии невозможна. Обновлять некуда (по исследованию у
каждой уязвимости «Описания» нет исправления для текущей версии) – режим «Исправленной версии нет – меры вместо
обновления» (ADR-0101 п. 4): в «Рекомендациях» строки о статусе исправления и обязательные меры оператора, строки
«Обновление …» нет. Образец на выдуманных данных (смешанный случай: одна уязвимость исправлена ниже цели, у другой
исправления нет; вторая найдена исследованием, а не Hub):


В Hub дефект создаётся из всех находок набора (карточка перечисляет их); текст одинаков из любой карточки набора.
Прежний формат 0.9.0–0.9.7 (заключение AppSec по ГОСТ Р КАПО, сводка и блок по каждой находке) приложение помнит
только для узнавания отметок «Дефект создан в Hub», поставленных до 0.9.8; у отметок по тексту 0.9.8–0.9.10 (со
строками AST, без группировки «Описания») карточка называет причину «формат текста 0.9.11».

## Справочники уязвимостей

Загружаются пользователем в приложение файлами, без интернета; в репозиторий и образ ВМ не входят.

| Справочник | Откуда | Что даёт |
|---|---|---|
| БДУ ФСТЭК России | выгрузка `vulxml.zip` с сайта БДУ (XML: идентификатор BDU, название и описание, уязвимое ПО и версии, CWE с русским названием, CVSS, уровень опасности, способ устранения, статус исправления, источники, связанные CVE) | описание, рекомендации и уровень опасности по-русски для SCA; русские названия CWE |
| CWE | каталог MITRE `cwec_latest.xml.zip` | описание класса слабости для SAST: в карточке и в справке для модели (в текст дефекта SAST с 0.9.6 не входит); в текст дефекта SCA по шаблону команды справка CWE автоматически не добавляется |
| CVE | фид NVD или архив CVE List (позже) | ссылки и описания по CVE |

Связка для SCA: по публичному идентификатору (CVE) из выгрузки находятся записи БДУ, где этот CVE указан
среди идентификаторов. Загрузка файла соответствия в интерфейсе остаётся как есть, но получение соответствия
AST → CVE целью плана не является.
