# Номера AST в выгрузке SCA: что известно (17.10.2026)

Справка, чтобы вернуться к теме. Тема отложена: сопоставление AST → CVE в план
не входит (п. 13 плана доработок снят). Основной сценарий SCA обходится без этих номеров:
[исследование компонентов](sca-component-mvp.md) идёт по имени и версии пакета.

## Что это за номера

- `AST-<год>-<цифры>` – внутренний номер уязвимости в базе AppSec.Track (SCA разработчика AppSec Solutions,
  ГК Swordfish Security; база Track.Feed). Публичные CVE, GHSA, BDU, NVD, OSV, SUSE хранятся у такой записи
  как алиасы – «идентификатор AST-уязвимости из другого источника, на основе которого она была создана»
  ([Политики](https://track-docs.appsec.global/security_policies/)).
- На странице уязвимости в Track показаны основной идентификатор, «Внутренний ID (AST)», связанные уязвимости,
  тип (уязвимость или вредоносное ПО) ([Поиск уязвимостей](https://track-docs.appsec.global/vulnerability_search/)).
  Записи типа «вредоносное ПО» CVE не имеют в принципе.
- Длина номера переменная: встречаются номера с шестью и с семью цифрами
  (вымышленный пример: `AST-2099-1234567`). Разбирать номер по шаблону `AST-\d{4}-\d+`.
- С релиза Track 4.3.0 (15.04.2026) основным идентификатором стал публичный, AST – внутренним
  ([релиз 4.3.0](https://track-docs.appsec.global/releases/release_4.3.0/)). В выгрузке Hub номер AST
  может стоять и у находок SCA, поэтому разбор его не исключает.

## Где связь AST → CVE есть и где её нет

| Где | Есть ли связь |
|---|---|
| Выгрузка AppSec.Hub (Excel) | нет: колонка `CVE id` – формула `HYPERLINK` на страницу `…/vulnerabilities/AST-…` во внутреннем Track |
| JSON-схема отчёта Hub | нет: только строки `cveId` и `cveLink` ([приложение 17](https://docs.appsec-hub.ru/2025.4/gi/appendix_2/)) |
| Открытые реестры (OSV, CVE.org, NVD) | нет: номера AST не публикуются |
| Страница уязвимости в Track | есть: основной идентификатор и связанные уязвимости; нужны права «Просмотр уязвимостей» |
| REST API Track (Swagger) и MCP (`/api/mcp`, заголовок `TRACK-API-TOKEN`) | вероятно есть; имена методов и полей не опубликованы; с 4.2.0 только по токену ([MCP](https://track-docs.appsec.global/mcp/), [интеграционный API](https://track-docs.appsec.global/integration_api/)) |
| JSON-отчёт Track, совместимый с DefectDojo (с 3.11) | не проверено: поля не описаны ([DefectDojo](https://track-docs.appsec.global/defectdojo/)) |

## Если к теме вернуться

1. Узнать у администратора Track: версию продукта; можно ли получить токен API только на чтение;
   образец JSON-отчёта (совместимого с DefectDojo) – есть ли в нём публичные идентификаторы.
2. Без доступа к Track возможен только подбор кандидатов через OSV по пакету и версии с отсевом по CWE,
   CVSS-вектору и версии исправления. Это предположение, а не соответствие: для `lodash 4.17.21` с
   исправлением в 4.18.0 подходят и CVE-2026-4800 (внедрение кода), и CVE-2026-2950 (загрязнение прототипа).
3. Модель хранения: статус `confirmed` – только алиас из Track; `probable` – единственный кандидат;
   `ambiguous` – несколько; `unmapped` – ни одного. `aliases` (та же уязвимость) и `related` (связанная запись)
   хранить раздельно; у каждой пары – источник и дата; связь бывает «многие ко многим».
4. Ручное соответствие уже есть: загрузка CSV «AST;CVE» на странице SCA (прежний сценарий).

Обращения к корпоративным системам и их API в проекте не делаются (решение владельца продукта);
пункты 1 и 3 потребуют его отдельного решения.
