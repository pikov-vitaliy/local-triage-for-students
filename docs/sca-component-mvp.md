# Исследование компонентов: порядок работы и план приёмки

**Результат приёмки ответа агента, 17.10.2026:** формат версии 2 и импорт работают, но проверка
контракта пока не исключает содержательных противоречий первоисточникам. До завершённого исследования
нужны исправления, описанные в повторной приёмке ответа.
Там разделены ошибки исследования, ограничения валидатора и путаница старого/нового импорта, приведены
контрольные примеры и критерии следующего этапа. Это открытая работа, а не подтверждение качества всех
сведений по успешному `exit 0`.

## Граница этой работы

Полученный Excel → задание внешнему агенту → исследование открытых источников → структурированный ответ
→ проверка и импорт → картина по компонентам → решение оператора AppSec. SBOM и его генераторы,
Dependency-Track, KEV и EPSS отложены. Hub остаётся только источником уже полученного файла.
AST не передаются в новое задание и не являются условием результата; исходная история остаётся локально.
За безопасность отвечает владелец. Здесь проектируются функциональность и качество данных.

Второй способ исполнения задания из приложения реализован в 0.9.13 (исследование провайдером из профиля, ADR-0105); прежний план описывал его так:
при наличии выхода в интернет, с согласия оператора и передачей публичных сведений без локальной привязки.
Файловый способ сохраняется; прежний замысел ADR-0067 заменён
принятым ADR-0105: с 0.9.13 сетевой режим – исследование
провайдером из профиля с согласия оператора. Первый вариант – с поисковым API выбранного провайдера, другие
провайдеры возможны позже.

## Что действительно есть во входе

С 0.10.0.dev22 экосистема и имя пакета строки берутся из сведений Hub о библиотеке принятого состояния Hub, Type и компонент выгрузки – запасной источник (ADR-0150). Исследования и решения прежней тройки при переходе переносятся к новой группе или уходят в архив; архив виден в истории компонента и в отчёте, но в главный ответ и действующее решение не входит.

Одна координата компонента (экосистема, имя и версия) может встречаться в нескольких строках находок. В колонке `CVE id` могут быть только внутренние
идентификаторы без публичных CVE. `Path`, `Artifact` и `Proxy` могут содержать заглушки без полезных путей зависимости.
Версии исправления из выгрузки – это предложения исходного источника, а не
подтверждённые актуальные релизы.

| Поле входа | Как использовать |
|---|---|
| Type, Component name, Component version | исходная идентичность компонента; входные значения сохраняются |
| Короткое имя Maven | требуется разрешить groupId:artifactId с источником и пояснением; не угадывать по популярности |
| Имя npm | сохранять имеющийся namespace, включая `@scope/name`; при коротком имени проверить, не утрачен ли scope |
| CVSS score | исходный балл без подтверждённой версии шкалы; не называть его автоматически CVSS 3.1 |
| Non-vulnerable versions | кандидат для исследования, не последняя стабильная и не готовый совет |
| CWE, Severity, Category | сведения первоначального анализатора; не доказывают конкретную публичную уязвимость |
| Application, Codebase, Issue id, Status | локальная привязка и история оператора |
| CVE id с внутренними номерами | локальное происхождение; в новое исследование не передавать |

Это выгрузка находок, а не полный состав ПО. Отсутствие компонента в ней не доказывает его отсутствия
в приложении. Исследование не имеет исходного кода и конфигурации: применимость публичного дефекта
к версии и эксплуатируемость в конкретном приложении показываются отдельно.

У npm также встречаются общие имена без scope, например `core`, `common`, `compiler`, `devtools`.
Синтаксически допустимое имя не доказывает, что это одноимённый пакет без scope. Агент проверяет точную
версию и namespace в первоисточнике, сохраняет способ разрешения и не объявляет найденный кандидат
идентичностью входного компонента только потому, что он первый в поиске.

## Что нужно получить из открытых источников

1. Точные координаты пакета и основание их разрешения.
2. Текущую версию из входа и последний подтверждённый стабильный релиз с датой проверки.
3. Доступность обновления, отдельно от наличия уязвимостей.
4. Поддержку текущей ветки: открытая, коммерческая, завершена, объявлена устаревшей или неизвестна.
   Возраст релиза и наличие более новой версии сами по себе не доказывают прекращение поддержки.
5. Публичные CVE/GHSA/advisory, применимость к текущей версии, затронутые диапазоны, условия и исправления.
6. Рекомендуемую версию или замену, ограничения совместимости и оставшиеся пробелы.
7. Источники, дату, охват и ошибки запросов. Недоступный источник не равен пустому успешному ответу.

Первичные источники: [запросы OSV по пакету и версии](https://google.github.io/osv.dev/quickstart/),
[метаданные реестра npm](https://github.com/npm/registry/blob/main/docs/responses/package-metadata.md),
[Maven Central и точные координаты](https://central.sonatype.org/search/rest-api-guide/),
официальные advisories, релизы и политики поддержки проектов. Например, у Spring различаются периоды
[открытой и коммерческой поддержки](https://spring.io/support-policy). Версия из `dist-tags.latest`
и минимальное исправление конкретной уязвимости имеют разный смысл.

## Решения оператора

| Действие | Что хранить |
|---|---|
| Оставить | обоснование достаточности текущего состояния |
| Обновить | целевую версию и обоснование |
| Заменить | выбранный компонент или направление замены и обоснование |
| Удалить | основание, почему зависимость не нужна |
| Принять риск | обоснование применительно к приложению; условия, ограничения и срок пересмотра при необходимости |
| Исследовать дополнительно | что именно нужно выяснить |

Решение хранится отдельно от исследованных фактов. «Принять риск» не удаляет CVE и не делает уязвимую
версию исправленной. Смена существенных фактов требует пересмотра решения, история сохраняется.
Изменение только локального номера AST не должно делать исследование компонента устаревшим.

## Отборы списка компонентов (0.9.9)

Решение – ADR-0096. Все отборы работают без сети, по сохранённым ответам
агента и загруженной выгрузке; недостающие факты – новое задание агенту.

1. **Найти компонент.** «Поиск» – по имени и версии, по идентификаторам публичных находок ответа (CVE, GHSA и
   другие псевдонимы) и по подтверждённым координатам. Найденный идентификатор – упоминание, а не доказательство
   применимости: находится и строка, где CVE неприменима.
2. **Отобрать по CVSS.** Балл строки – вывод агента: наибольший балл среди находок с применимостью «да»;
   оспоренность его не убирает (пометка «есть оспоренные»), решения оператора о применимости в балл не входят.
   Выберите версию шкалы (2.0, 3.0, 3.1, 4.0 или любая), нижнюю границу «не ниже» или «строго выше» и верхнюю «не
   выше»; нижняя больше верхней – пустая выборка с пояснением. Готовая ссылка – «CVSS 3.1 строго выше 7».
3. **Строки без балла** в отбор по CVSS не входят, у них свои отборы: «не исследован», «применимость не
   установлена», «применимых не найдено», «балл неизвестен». «Оценка неполная» – балл есть не у всех применимых
   находок выбранной версии: строка входит в отбор по известному наибольшему баллу.
4. **Поддержка, совет агента и действие оператора** – три независимых отбора; отдельно – «срок пересмотра
   наступил» и прежнее «только требующие пересмотра». У неисследованной строки поддержки и совета нет.
5. **Свежесть.** «Ответ агента принят больше 30 / 90 дней назад» – дата загрузки ответа в приложение (повторная
   загрузка того же содержания её обновляет), а не повторная проверка источников агентом.
6. **Счётчики сводки** («Уязвимые», «Неполные», «С пробелами», «Поддержка неизвестна», «Не исследованы», «Требуют
   пересмотра» и другие) – ссылки на свои выборки.

Решение по находкам SCA и перенос в Hub остаются в карточке находки SCA: там пакетное решение на версию и дефект
набора (ADR-0091); блок «Исследование компонента» в ней ведёт в
карточку компонента, а «Где используется» в карточке компонента – к находкам SCA этой версии.

## Проверяемые основания ответа

`research_coverage` содержит цель `purpose`, запрос `query` с экосистемой, координатами и текущей версией,
ссылки `source_refs`, дату, результат и полноту. Проверка реестра релизов не подменяет поиск уязвимостей.
Уточнение короткого имени требует `identity_resolution.basis` и успешного протокола идентификации.
`package_advice.source_refs` связывает целевую версию с источником её публикации в реестре или официальном
релизе; наличие одной ссылки на CVE этого не заменяет. Приложение проверяет связь полей, а не скачивает
страницу повторно и не объявляет истинность её содержания подтверждённой.

Порядок версий проверяется для npm SemVer и ограниченного подмножества Maven: числовые сегменты и обычные
alpha/beta/milestone/rc/snapshot/final/ga/release/sp. Это не полный Maven ComparableVersion.
Неизвестные суффиксы поставщика не сравниваются наугад: состояние обновления остаётся неизвестным,
кандидат описывается в пояснении без недоказанного совета обновить. Основания:
[порядок версий Maven](https://maven.apache.org/pom.html#version-order-specification),
[SemVer npm](https://docs.npmjs.com/cli/v11/using-npm/semver/).

## Порядок реализации и приёмка

1. Зафиксировать новый контракт: неизменяемые входные строки, манифест задания, публичные находки,
   версии, поддержка, советы, источники и охват. Модель SCA отделить от старых строк анализатора.
2. Сформировать задание без AST и комплект с заготовкой, схемой и проверяющей программой.
   Программа проверки у агента и при импорте использует одни правила. Протокол агента не принимается на веру.
3. Добавить отдельное хранение исследования и решений. Старые ответы и решения сохраняются;
   старый ответ не получает новый уровень подтверждения автоматически.
4. Показать исследование по компонентам: текущая/актуальная/рекомендуемая версии, поддержка,
   публичные уязвимости, полнота и решение оператора. Не сводить всё к одному «неясно».
5. Проверить изолированный полный цикл и рабочий экспорт всех строк без AST; затем обновить приложение.

Механические проверки: все входные строки ровно по одному разу, точные версии, привязка к сохранённому
заданию, допустимые состояния, отсутствие внутренних идентификаторов, связь утверждений с источниками,
согласованность вывода с находками, невозможность назвать ошибку источника успешной проверкой,
отсутствие молчаливой обрезки. Корректная неполнота принимается с явными причинами и не запускает
бесконечный повтор. Неправильный ответ получает машинный отчёт ошибок до сохранения.

Нельзя обещать истинность любого утверждения модели по одному правильному JSON. Формат, привязку и
логические противоречия проверяет программа; происхождение и пределы содержательных выводов видны оператору.
Это реализация критериев проверок и сбора подтверждений PO.4
[NIST SSDF 1.1](https://csrc.nist.gov/pubs/sp/800/218/final), а не заявление о соответствии всему стандарту.

Сценарий реализован для версии 0.4.0. Сохранены границы текущего MVP и последующего этапа;
результаты приёмки – в протоколе проверки.
